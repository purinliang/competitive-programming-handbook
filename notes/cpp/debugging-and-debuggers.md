# 调试与调试器

> 最近修订：2026-08-16 23:50 +10:00（未审阅）

程序没有得到预期结果时，只盯着代码反复猜测通常很慢。**调试**是收集程序实际行为的证据，再根据证据定位错误的过程；**调试器**是帮助暂停程序、逐步执行并观察状态的工具。

调试不属于 [编译](compilation.md) 的某个阶段，也不保证自动找出错误。它让我们看见程序“实际上做了什么”，再与“本来应该做什么”比较。

## 先判断错误发生在哪一类

不同错误应从不同位置开始检查。

### 编译错误

源代码没有成功构建成程序，例如：

- 漏写分号或花括号；
- 使用了没有声明的名称；
- 调用函数时参数类型或数量不匹配；
- [链接](linking.md) 时找不到某个函数的定义。

编译器通常会给出文件名、行号和诊断信息。先处理最前面的错误，因为一个早期语法错误可能引发后面许多连锁诊断。

### 运行时错误

程序已经成功构建，但运行过程中异常终止，例如：

- 整数除以零；
- 访问非法内存；
- 递归过深导致调用栈耗尽；
- 主动触发断言失败。

在线评测通常把这类结果归为运行时错误（Runtime Error，RE）。调试器能够在异常附近暂停，并显示当时的调用栈与变量值。

### 逻辑错误

程序能够运行到结束，却计算出错误答案。例如循环少处理一个元素、比较方向写反、状态没有正确初始化。在线评测最常见的表现是答案错误（Wrong Answer，WA）。

逻辑错误不会自动触发编译器或操作系统报错。需要构造小数据，逐步比较中间状态和手算结果。

超时（TLE）与内存超限（MLE）通常来自复杂度、死循环、数据规模估计或资源使用问题。它们有时也能借助调试器定位，但首先应检查算法与复杂度。

## 用最小数据复现

开始单步执行以前，先找到一个足够小、能够稳定产生错误的输入。

例如，一个程序要计算 $n$ 个整数之和，却漏掉最后一个元素：

```cpp
int sum = 0;

for (int i = 1; i < n; ++i) {
    sum += a[i];
}
```

使用下面的数据就足以复现：

```text
3
10 20 30
```

正确答案是 `60`，错误程序输出 `30`。这比使用十万个随机数更适合调试：每一步都能手算，也能迅速看到循环从未到达 `i == n`。

## 断点

**断点**告诉调试器：程序执行到这个位置时先暂停。

对上面的循环，可以在 `sum += a[i];` 所在行设置断点。程序暂停后，可以查看：

- 当前执行到哪一行；
- `i`、`n` 与 `sum` 的值；
- `a[i]` 当前是哪一个元素；
- 程序是从哪个函数调用到这里的。

断点不会修改算法。它只是让运行过程停在一个值得观察的位置。若循环次数很多，可以使用条件断点，例如只在 `i == n - 1` 时暂停。

## 单步执行

调试器通常提供三种常用的单步操作，具体按钮名称可能因工具不同而略有差异：

- **步过**（step over）：执行当前行；若当前行调用函数，不进入函数内部；
- **步入**（step into）：当前行调用函数时，进入被调用函数；
- **步出**（step out）：继续执行到当前函数返回，并回到调用者。

检查普通循环时主要使用步过。怀疑某个函数内部计算错误时使用步入；确认当前函数没有问题后，可以用步出返回上一层。

单步执行时始终问两个问题：这一行执行以前，各变量应该是什么？执行以后，哪些变量应该怎样变化？第一次出现实际值与预期值不一致的位置，通常比最终错误输出更接近原因。

## 查看变量

程序暂停时，可以查看当前作用域内的局部变量和可访问的全局变量。许多调试器还支持：

- 把表达式加入监视列表，持续观察它的值；
- 展开数组、`vector`、结构体或对象；
- 临时计算表达式，例如 `i <= n`；
- 观察变量在什么时候改变。

对求和错误，可以同时监视 `i`、`n`、`a[i]` 和 `sum`。当循环在 `i == n - 1` 后直接结束，就能确认问题来自条件 `i < n`，而不是加法本身。

## 调用栈

程序调用一个函数时，会在 [调用栈](function-call-stack.md) 中留下对应的函数调用。调试器的调用栈视图会显示：

- 当前暂停在哪个函数；
- 这个函数由谁调用；
- 每一层调用发生在哪一行；
- 各层自己的参数与局部变量。

递归错误、错误的函数参数和运行时崩溃尤其需要调用栈。如果同一个递归函数重复出现许多层，应检查递归规模是否不断缩小，以及终止条件能否被到达。

## 输出也可以帮助调试

没有调试器时，可以暂时输出关键状态：

```cpp
cerr << "i = " << i << ", sum = " << sum << '\n';
```

`cerr` 是标准错误输出流，通常不会与 `cout` 共用缓冲策略，但在线评测是否忽略它取决于平台。提交前应删除不需要的调试输出，不能假定评测系统一定不会检查或限制它。

使用输出调试时也要控制信息量。只输出能验证当前假设的变量；成千上万行未经筛选的日志往往会把真正的异常淹没。

## 修正并重新验证

定位问题后，把循环边界改成闭区间：

```cpp
for (int i = 1; i <= n; ++i) {
    sum += a[i];
}
```

下面是完整的修正版：

```cpp
#include <bits/stdc++.h>
using namespace std;

const int MAXN = 2e5 + 5;

int n;
int a[MAXN];

void solve() {
    cin >> n;

    for (int i = 1; i <= n; ++i) {
        cin >> a[i];
    }

    int sum = 0;

    for (int i = 1; i <= n; ++i) {
        sum += a[i];
    }

    cout << sum << '\n';
}

int main() {
    solve();
    return 0;
}
```

修正后不仅要重新运行原来的失败数据，还要检查最小规模、边界值和其他正常数据。一个修改可能修复当前样例，却引入新的边界错误。

## 需要记住什么

1. 编译错误、运行时错误与逻辑错误分别发生在什么情况下？
2. 为什么小而稳定的失败输入更适合调试？
3. 断点会不会改变程序原本的算法？
4. 步过、步入和步出分别适合什么情况？
5. 调用栈能帮助回答哪些问题？
6. 找到并修复错误后，为什么还要重新检查边界数据？
