# volatile

> 最近修订：2026-08-16 14:43 +10:00（未审阅）

编译器通常可以省略看起来没有影响的内存读写：若程序刚把一个值存进变量，随后
重复读取它，机器代码未必真的每次访问内存。但某些地址可能连接硬件寄存器，读取
本身就有外部意义，值也可能在普通 C++ 代码以外改变。

`volatile` 告诉实现，对这个对象的访问具有特殊的可观察性要求，不能把它当作普通
内存值任意省略或合并。它主要服务于底层系统和嵌入式环境，不是竞赛中实现并发、
优化速度或防止变量改变的工具。

## volatile 对象

把限定符写在类型前：

```cpp
volatile int status = 0;
```

通过 `volatile` 左值读写 `status` 时，实现需要按照其 volatile 访问语义处理。
例如下面的循环会反复读取 `status`，而不是理所当然地把第一次读取结果永久缓存：

```cpp
while (status == 0) {
}
```

这只展示关键字的意图。若另一个普通线程同时修改 `status`，这段代码仍然存在数据
竞争，行为未定义；`volatile` 不能把它变成正确的线程通信。

## 典型用途

`volatile` 常见于实现定义的底层接口，例如把某个地址映射到硬件状态寄存器：

```cpp
volatile unsigned int* status_register;
```

每次读取这个地址可能查询设备新状态，每次写入也可能触发设备行为。这类含义依赖
平台文档、编译器与硬件，单靠标准 C++ 代码不能凭空决定某个地址就是寄存器。

信号处理等特殊环境也可能使用 `volatile sig_atomic_t` 与受严格限制的处理函数协作。
这些都是平台或标准库专门规则，不应推广成“任何异步修改都加 volatile”。

## 不能保证原子性

`volatile` 不会让复合操作变成不可分割的一步：

```cpp
volatile int counter = 0;
counter++;
```

自增仍然包含读取、计算和写回。多个线程并发执行可能互相覆盖，而且普通 C++ 数据
竞争本身就是未定义行为。

线程之间共享计数应使用 `std::atomic<int>` 或由互斥量保护：

```cpp
atomic<int> counter{0};
counter++;
```

算法竞赛很少需要多线程；这里只为了排除“volatile 等于原子”的错误理解。

## 不能建立线程同步顺序

线程通信不仅需要单次读写不可分割，还需要规定多个操作之间的可见顺序。
`volatile` 不是 C++ 内存模型中的同步操作，不提供互斥，也不建立线程间的
happens-before 关系。

因此下面的经典想法并不正确：一个线程先写普通数据，再把 `volatile bool ready`
设为真；另一个线程等待 `ready` 后读取数据。两个线程仍可能发生数据竞争，编译器
和处理器也不必提供所期待的同步保证。

## 与 const 的区别

`const` 限制程序通过当前接口修改对象，`volatile` 约束实现怎样对待访问。二者可以
同时出现：

```cpp
const volatile int status = 0;
```

这表示当前代码不能通过这个名称普通赋值，但每次读取仍要按 volatile 语义处理。
它适合“程序只读、外部设备可能改变”的概念，并不矛盾。

两者都属于类型限定符，却回答不同问题：

| 限定符 | 主要含义 |
| --- | --- |
| `const` | 不允许通过该接口普通修改对象 |
| `volatile` | 对访问保留实现要求的可观察行为 |

## 不能用于加速

`volatile` 往往限制编译器缓存和消除访问，可能让代码更慢，而不是更快。它也不会
阻止编译器进行一切优化；实现仍可在不违反 volatile 访问规则和程序可观察行为的
范围内优化其他代码。

若担心竞赛代码中的某个变量“被优化没了”，首先检查程序是否存在未定义行为或
是否真的使用了计算结果。正确的普通 C++ 程序不需要靠 `volatile` 阻止编译器做出
错误优化。

## 完整代码

下面只演示 volatile 对象的声明、写入与读取。输入输出由同一线程完成，所以程序
并不需要 `volatile`；删除关键字，结果不变：

```cpp
#include <bits/stdc++.h>
using namespace std;

void solve() {
    int input;
    cin >> input;

    volatile int observed = input;
    cout << observed << '\n';
}

int main() {
    solve();
    return 0;
}
```

输入：

```text
42
```

输出：

```text
42
```

这也说明语法上能够使用，不等于在普通竞赛程序中有使用理由。

## 常见错误

### 用 volatile 实现线程通信

它不保证原子性、不消除数据竞争，也不建立线程同步顺序。并发共享状态使用原子
类型或锁。

### 把 volatile 当成 const

`volatile` 对象仍然可以由程序写入；`const` 才限制通过当前接口修改。

### 认为 volatile 会让代码更快

它通常限制部分优化，主要为外部可观察访问服务，不是性能提示。

### 给普通竞赛变量全部加 volatile

这会增加噪声和访问限制，却没有修复算法、边界或未定义行为。本仓库模板不使用
`volatile`。

## 需要记住什么

1. `volatile` 试图解决哪一类“值可能在普通代码外变化”的访问问题？
2. 它能否保证 `counter++` 原子执行？
3. 它能否消除线程数据竞争或建立同步顺序？
4. `const` 与 `volatile` 分别限制什么？二者能否同时出现？
5. `volatile` 是性能优化提示吗？
6. 普通算法竞赛代码为什么几乎不需要它？
