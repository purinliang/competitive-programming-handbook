# 编译

> 最近修订：2026-08-16 15:35 +10:00（未审阅）

C++ 源代码是供人和语言工具阅读的文本，处理器最终执行的却是目标平台的机器指令。
**编译**负责分析预处理后的翻译单元，检查 C++ 语法和语义，并为目标平台生成
目标代码。

日常说“编译程序”时，常把预处理、编译、汇编和链接整套构建过程都包括在内；
需要判断错误来源时，本篇使用更窄的含义：编译器分别处理每个翻译单元并产生目标
文件，随后再由链接器把它们组成可执行文件。

## 编译器检查什么

编译器首先需要把记号解析成 C++ 程序结构，并验证语言规则，例如：

- 括号、分号与声明语法是否成立；
- 名称是否在当前位置声明且可访问；
- 表达式中的类型能否参与相应运算；
- 函数调用的参数能否匹配某个声明；
- 返回语句是否符合函数返回类型。

下面的代码在编译阶段就能判定错误：

```cpp
int value = "hello";
```

字符串字面量不能按这种方式初始化 `int`。程序不需要运行到这一行，编译器已经
拥有判断所需的类型信息。

编译成功只表示代码满足当前构建能检查到的语言与接口规则，不代表算法正确，也不
代表任何输入都不会越界、除以零或超时。

## 每个翻译单元独立处理

[预处理](preprocessing.md) 后，一个 `.cpp` 与它包含的头内容形成一个翻译单元。
编译器通常分别处理各个翻译单元：

```text
main.cpp  →  main.o
math.cpp  →  math.o
```

处理 `main.cpp` 时，编译器不会自动阅读另一个 `math.cpp` 来猜函数类型。若当前
文件要调用其中定义的函数，需要先看见相应声明，通常由共同头文件提供：

```cpp
int add(int a, int b);
```

声明告诉编译器调用接口；另一个翻译单元中的定义负责提供函数实现。两者是否最终
对应，由后续链接继续检查。

## 目标文件

翻译单元经过编译和目标代码生成后，通常得到 `.o` 或 `.obj` **目标文件**。它
可以包含：

- 当前翻译单元生成的机器代码与数据；
- 已定义符号的信息；
- 仍需由其他文件或库提供的外部符号引用；
- 链接时调整地址所需的信息。

目标文件通常还不是可以直接运行的完整程序。它可能调用了标准库函数或其他
`.cpp` 中的函数，却尚未知道这些实现最终位于可执行文件的哪个地址。

机器代码依赖目标处理器、操作系统接口和 ABI。相同 C++ 源码可以在不同平台重新
编译，但一个平台生成的目标文件通常不能原样拿到另一平台链接和执行。

## 使用编译器驱动

GNU 竞赛环境常用 `g++`。只编译、不进行最终链接可以写：

```text
g++ -std=c++17 -O2 -Wall -Wextra -c main.cpp -o main.o
```

常见选项含义是：

| 选项 | 作用 |
| --- | --- |
| `-std=c++17` | 按 GNU 编译器支持的 C++17 模式编译 |
| `-O2` | 启用一组常用优化 |
| `-Wall -Wextra` | 开启一组有价值的警告 |
| `-c` | 生成目标文件后停止，不进行最终链接 |
| `-o main.o` | 指定输出文件名 |

选项属于具体编译器接口，不是 C++ 源语言的一部分。线上评测使用什么标准版本、
优化和扩展，由平台编译命令决定；提交代码不能假定本地额外选项在评测中也存在。

## 编译器驱动做的不只编译

如果省略 `-c`：

```text
g++ -std=c++17 -O2 main.cpp -o main
```

`g++` 作为**编译器驱动**，通常会依次协调预处理、编译、汇编和链接，最后得到
可执行文件。命令行只出现一次 `g++`，不表示内部只有一个阶段。

常用的阶段观察选项包括：

```text
g++ -E main.cpp              只观察预处理结果
g++ -S main.cpp              生成汇编文本
g++ -c main.cpp              生成目标文件
g++ main.o -o main           链接目标文件
```

具体输出名和细节由平台决定。这些命令用于建立过程直觉，不要求为了参加竞赛背诵
所有编译器选项。

## 优化不改变合法程序含义

`-O2` 允许编译器在保持标准所要求可观察行为的前提下改写机器代码，例如消除重复
计算、内联函数或重新安排不影响结果的操作。优化目标是产生更高效代码，不会把
一个 $O(n^2)$ 算法自动变成正确的 $O(n\log n)$ 算法。

若源程序触发未定义行为，C++ 已经不再规定必须出现什么结果，编译器可以基于
“正确程序不会发生这种行为”的假设进行优化。调低优化后偶尔看似正常，不是程序
正确的证据；应修复越界、悬空引用、有符号溢出等根因。

## 警告与错误

编译错误使目标文件无法产生。警告通常不会阻止构建，却提示可疑代码，例如未使用
变量、可能缺少返回路径或隐式转换风险。

警告不是语言证明：没有警告不等于没有错误，某条警告也不一定适用于当前意图。
竞赛本地构建开启常用警告并逐条理解，比无条件忽略或机械开启所有警告更有效。

线上评测常把源代码无法成功构建记为 Compile Error（CE）。函数已经声明但没有
任何目标文件提供定义，通常不是本篇的编译错误，而会在下一步表现为链接错误。

## 编译与运行

构建成功以后，操作系统才加载可执行文件并开始运行 `main`。因此错误阶段不同：

| 阶段 | 典型问题 |
| --- | --- |
| 编译 | 语法错误、类型不匹配、名称未声明 |
| 链接 | 函数声明存在但定义缺失、重复定义 |
| 运行 | 越界导致崩溃、除零、读入错误 |
| 算法判定 | 输出错误、超时、超内存 |

定位报错时先看它来自编译器、链接器还是已经运行的程序，不要把所有失败都统称为
“代码运行不了”。

## 完整代码

下面是一个能通过 C++17 编译并运行的独立翻译单元：

```cpp
#include <bits/stdc++.h>
using namespace std;

int add(int a, int b) {
    return a + b;
}

void solve() {
    int a;
    int b;
    cin >> a >> b;
    cout << add(a, b) << '\n';
}

int main() {
    solve();
    return 0;
}
```

GNU C++17 可以直接构建：

```text
g++ -std=c++17 -O2 main.cpp -o main
```

输入：

```text
3 5
```

输出：

```text
8
```

若只加 `-c`，会得到目标文件而不是可直接运行的最终程序。

## 常见错误

### 把编译成功当成答案正确

编译器检查语言规则，不知道题目要求的算法结论。正确性仍需证明和测试。

### 认为编译器会自动阅读所有 cpp

翻译单元独立处理。调用接口需要声明，最终实现需要参与链接。

### 把目标文件当成完整可执行文件

目标文件仍可能含有未解析符号和待调整地址，需要链接器组成最终程序。

### 依赖本地特有编译选项

评测机的标准库、扩展和编译参数可能不同。应以题目声明的环境为准。

### 用关闭优化掩盖未定义行为

表现变化只说明程序不可靠，不能把某个构建模式的偶然结果当成保证。

## 需要记住什么

1. 狭义编译接收什么，产生什么？
2. 编译器能检查哪些语言问题，又不能证明什么？
3. 为什么每个翻译单元需要先看见所调用函数的声明？
4. 目标文件为什么通常还不能直接运行？
5. `g++` 为什么一次命令可以协调多个构建阶段？
6. `-E`、`-S`、`-c` 分别在哪个位置停止？
7. 优化为什么不能修复渐进复杂度或未定义行为？
8. 编译错误、链接错误和运行错误应怎样区分？
