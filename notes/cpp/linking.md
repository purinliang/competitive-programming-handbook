# 链接

> 最近修订：2026-08-16 15:45 +10:00（未审阅）

每个翻译单元能够独立编译成目标文件，但其中的函数调用和全局对象引用可能指向
其他文件或标准库。**链接**负责把目标文件和需要的库组合起来，解析跨文件名称，
调整最终地址并产生可执行文件。

链接解释了两类常见报错：代码明明看见了函数声明，最后却提示 undefined
reference；或者每个源文件都能单独编译，合在一起却提示 multiple definition。

## 声明与定义

函数声明告诉编译器接口：

```cpp
int add(int a, int b);
```

函数定义提供实现：

```cpp
int add(int a, int b) {
    return a + b;
}
```

调用所在翻译单元只需先看到声明，就能生成一次对 `add` 的外部引用。最终参与链接
的目标文件中必须存在与它对应的定义。

头文件通常保存声明，源文件保存定义：

```text
math.h    声明 add
math.cpp  定义 add
main.cpp  包含 math.h 并调用 add
```

若 `math.cpp` 没有参与构建，`main.cpp` 仍可能顺利产生目标文件，但链接器找不到
`add` 的实现。

## 符号解析

目标文件会记录自己提供和需要的**符号**。可以把链接器的核心任务简化为：

1. 收集各目标文件与库提供的定义；
2. 为每个外部引用寻找匹配定义；
3. 检查不能共存的重复定义；
4. 安排代码和数据位置，并修正对最终地址的引用；
5. 写出可执行文件或另一个库。

C++ 函数可以重载，编译器通常会把函数名、参数类型等编码进底层符号名称，这常称
名称修饰（name mangling）。具体编码属于编译器 ABI，不由 C++ 标准规定；不要在
普通源码中手写猜测后的底层名称。

## undefined reference

如果有声明和调用，却没有任何参与链接的文件提供匹配定义，GNU 链接器常报告
`undefined reference`：

```cpp
int add(int a, int b);

int main() {
    return add(2, 3);
}
```

这段代码拥有足够信息编译调用，但单独链接时缺少 `add` 定义。

常见原因包括：

- 忘记把实现所在 `.cpp` 或目标文件加入命令；
- 声明与定义的参数类型、命名空间或 `const` 等签名不一致；
- 忘记链接所需库；
- 条件编译排除了真正定义。

看到错误时应核对缺失的完整符号和构建输入，而不是在调用处再复制一个可能不一致
的临时实现。

## multiple definition

普通具有外部链接的函数或对象若在多个翻译单元各有一个不允许重复的定义，链接器
通常报告 `multiple definition`。

例如把普通函数完整定义在没有 inline 语义的公共头中：

```cpp
// bad.h
int add(int a, int b) {
    return a + b;
}
```

两个 `.cpp` 都包含这个头，就各自产生一份 `add` 定义。修复方式通常是：

- 头文件只留声明，把一次定义放进某个 `.cpp`；
- 若函数确实适合在头中定义，按规则使用 `inline`；
- 模板定义按模板规则放在需要可见的位置。

不能简单地把链接器“允许重复定义”的特殊选项当作通用修复，因为不同定义之间的
行为本来就没有统一含义。

## 单一定义规则

C++ 的**单一定义规则**（One Definition Rule，ODR）约束实体可以在程序中拥有
多少定义。普通非 inline 函数或具有外部链接的普通对象通常只能有一个程序定义；
类定义、模板和 inline 实体允许按严格条件在多个翻译单元出现相同定义。

“内容看起来差不多”不够。允许重复的定义仍需满足语言规定的一致性条件。违反
ODR 的程序有些会被链接器发现，有些不要求实现诊断，却仍然不是可靠程序。

竞赛单文件代码很少直接遇到跨翻译单元 ODR 问题，但阅读工程项目和理解 inline
时需要知道这条边界。

## 链接与名称可见范围

作用域决定名称在源代码哪里可见，**链接属性**描述不同作用域或翻译单元中的声明
是否指向同一个实体。二者不是一回事。

命名空间作用域的某些 `static` 声明具有内部链接，使名字只对应当前翻译单元中的
实体：

```cpp
static int helper(int x) {
    return x * x;
}
```

另一个 `.cpp` 可以拥有自己的同名内部实体，不参与跨文件符号合并。这里的
`static` 用法不同于 [static 局部变量](static-local-variables.md) 的“跨调用保留
对象”；同一个关键字参与了不同语法规则。

竞赛单文件不需要为了所有辅助函数增加 `static`。内部链接、匿名命名空间和模块
可见性属于工程组织细节，本篇只需认出链接属性与作用域、生命周期不同。

## 库

库把已经编译的实现组织起来，供程序链接。可以粗略区分：

- 静态库：需要的目标代码在链接时进入最终产物；
- 动态库：可执行文件记录依赖，程序装载或运行时由系统提供共享库实现。

标准库的输入输出、容器支持等实现也需要进入完整构建。使用 `g++` 驱动链接 C++
程序时，它会按配置加入所需 C++ 运行库；直接用更底层的链接命令则需要自己处理更
多参数。

静态或动态描述的是库交付与装载方式，不决定 C++ 函数是否写了 `static`，也不等
同于对象的静态存储期。

## 完整多文件示例

头文件 `math.h` 只声明接口：

```cpp
#ifndef MATH_H
#define MATH_H

int add(int a, int b);

#endif
```

源文件 `math.cpp` 提供一次定义：

```cpp
#include "math.h"

int add(int a, int b) {
    return a + b;
}
```

`main.cpp` 通过同一个头取得声明：

```cpp
#include <bits/stdc++.h>
using namespace std;

#include "math.h"

void solve() {
    int a;
    int b;
    cin >> a >> b;
    cout << add(a, b) << '\n';
}

int main() {
    solve();
    return 0;
}
```

分别编译并链接：

```text
g++ -std=c++17 -O2 -c math.cpp -o math.o
g++ -std=c++17 -O2 -c main.cpp -o main.o
g++ main.o math.o -o main
```

也可以让驱动一次协调：

```text
g++ -std=c++17 -O2 main.cpp math.cpp -o main
```

输入 `3 5` 时输出 `8`。如果最后一条命令漏掉 `math.cpp`，调用仍能编译，却会在
链接时找不到 `add`。

## 常见错误

### 只有声明，没有参与链接的定义

检查实现文件或库是否真的进入命令，以及声明与定义签名是否完全对应。

### 在公共头中定义普通外部函数

多个翻译单元包含后可能产生重复定义。使用一次 `.cpp` 定义，或在适合的场景按
inline、模板规则组织。

### 把 static 的不同含义混在一起

命名空间作用域 `static` 可影响链接属性；函数内 `static` 主要影响对象存储期。
必须结合声明位置判断。

### 把链接成功当成程序可正确运行

链接器只解决组成程序所需的定义与地址，不验证算法、输入范围或运行时内存安全。

## 需要记住什么

1. 链接接收哪些输入，最终产生什么？
2. 声明为什么足以编译调用，却不足以完成链接？
3. undefined reference 常见于哪些缺失或不一致？
4. 公共头中的普通函数定义为什么可能产生 multiple definition？
5. 单一定义规则是否允许任意多个“差不多”的定义？
6. 作用域与链接属性分别描述什么？
7. 命名空间作用域 `static` 与函数内 `static` 的重点有什么不同？
8. 静态库、动态库与 `static` 关键字是否是同一概念？
