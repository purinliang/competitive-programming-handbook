# 编译器与解释器

> 最近修订：2026-08-16 23:46 +10:00（未审阅）

人能读懂下面的 C++ 源代码：

```cpp
int answer = 3 + 5;
```

处理器却不能直接按照 C++ 语法执行这行文字。程序运行以前或运行过程中，必须有工具把源代码转换成计算机能够执行的操作。

**编译器**与**解释器**是完成这种转换的两种基本执行模型。本篇只解释两者的核心区别；C++ 程序具体经历的[编译](compilation.md)与[链接](linking.md)在后文分别展开。

## 编译器

编译器先读取源程序，再把它翻译成目标代码。经过后续必要步骤，得到可以运行的程序：

```text
源代码 → 编译器 → 目标代码或可执行程序 → 运行
```

算法竞赛中的 C++ 通常采用这种方式。提交源代码后，在线评测系统先使用指定的 C++ 编译器和语言标准构建程序；构建成功后，才使用测试数据运行它。

如果代码存在语法错误、名称找不到或类型不匹配等问题，编译器会报告**编译错误**，程序不会进入正常运行阶段。

编译器能够在看到整个翻译单元时分析和优化代码。生成的可执行程序运行时通常不再需要逐行读取原来的 C++ 源文件。

## 解释器

解释器在程序运行时读取程序表示，并执行相应操作。最简化的模型是：

```text
源代码或中间表示 → 解释器边读取边执行
```

在这种模型中，执行环境负责理解程序表示，而不是提前只生成一个完全独立的本机可执行程序。解释器也会检查语法、建立内部结构或生成中间表示；“解释”并不等于机械地逐个读取源文件中的文本行。

解释型环境往往便于交互式执行少量代码，但运行程序时仍需要相应的解释环境。

## 核心区别

可以先用下面的对比建立直觉：

| 问题 | 编译模型 | 解释模型 |
| --- | --- | --- |
| 主要转换何时发生 | 程序运行以前 | 程序运行过程中 |
| 通常运行什么 | 提前生成的目标程序 | 由解释环境读取的程序表示 |
| 错误何时发现 | 许多错误在构建时发现 | 一些错误可能到执行相关部分时才发现 |
| 竞赛 C++ 的常见方式 | 是 | 通常不是 |

这张表描述的是基本模型，不是所有语言实现都必须遵守的绝对边界。

## 语言不等于唯一实现方式

“C++ 是编译型语言”“某语言是解释型语言”可以帮助初步分类，但语言本身是一套语法和语义规则，不会强制所有实现只能采用一种执行策略。

现代实现可能混合多种方法：

- 先把源代码编译成中间表示，再由虚拟机解释执行；
- 运行时把经常执行的部分即时编译成本机代码；
- 先解释少量代码，同时在后台编译其余部分。

运行时进行的编译通常称为**即时编译**（Just-In-Time compilation，JIT）。因此，讨论具体程序怎样执行时，应当说明使用的实现与工具，而不是只根据语言名称推断。

## 竞赛中的 C++ 程序

对当前教程中的 C++17 程序，可以先采用下面的实用模型：

```text
main.cpp
  ↓ 预处理与编译
目标文件
  ↓ 链接
可执行程序
  ↓ 使用测试数据运行
输出结果
```

例如，GNU C++ 常使用下面的命令构建源文件：

```text
g++ -std=c++17 main.cpp -o main
```

这条命令调用编译器驱动程序，最终生成名为 `main` 的可执行程序。详细选项和构建阶段会在[编译](compilation.md)中解释。

在线评测中，编译器、操作系统、处理器架构、语言标准与编译选项共同构成程序运行环境的一部分。同一份超出标准保证范围的代码，不能因为在自己的电脑上得到某个结果，就假定所有评测环境都会相同。

## 常见误解

### 编译器只是检查语法

检查语法只是编译工作的一部分。编译器还要分析名称和类型，并生成目标代码；它也可能在保持标准规定行为的前提下优化程序。

### 解释器一定逐行执行源文件

真实解释器可能先解析完整程序、生成字节码或建立抽象语法树，再执行内部表示。“边读取边执行”只是帮助区分执行时机的简化模型。

### 编译成功就说明程序正确

编译器只能检查它能够依据语言规则发现的问题。数组越界、除以零、算法错误或输出格式错误仍可能在运行或评测时暴露。怎样定位这些问题属于后续“调试与调试器”的内容。
