# 预处理

> 最近修订：2026-08-16 15:25 +10:00（未审阅）

C++ 编译器真正分析类型、表达式和函数以前，源文件会先经过**预处理**。以 `#`
开头的预处理指令能够包含头文件、定义宏或根据条件保留一部分代码；处理结果再
进入后续编译。

预处理器主要处理记号和文件内容，不理解 `int` 是否适合某个表达式，也不会执行
程序的运行时控制流。把这一阶段与普通 C++ 分开，才能理解为什么 `#include` 不写
分号、宏没有类型，以及条件编译为什么不能替代 `if`。

## 从源文件到翻译单元

对日常竞赛代码，可以把前半段构建过程简化为：

```text
源文件
  ↓ 预处理：处理 include、宏和条件编译
预处理后的翻译单元
  ↓ 编译与生成目标代码
目标文件
  ↓ 链接
可执行文件
```

一个 `.cpp` 连同它通过 `#include` 引入的内容，经预处理后形成供编译器处理的
翻译单元。头文件不是预先独立“自动加入项目”的；源文件通过包含指令建立依赖。

真实 C++ 标准规定了更细的翻译阶段，编译器也可能把多个步骤合并实现。本篇模型
用于理解代码和错误出现在哪一层，不代替完整编译原理。

## 预处理指令

指令通常从逻辑行开头的 `#` 开始：

```cpp
#include <iostream>
#define LIMIT 100
#if LIMIT > 50
#endif
```

它们不是普通 C++ 语句，因此末尾不写分号。预处理器先识别指令并产生新的记号
序列；被条件排除的代码不会进入后续语法和类型检查。

反斜杠可以让一条预处理指令延续到下一物理行：

```cpp
#define ADD(a, b) \
    ((a) + (b))
```

这在多行宏中常见，也增加了维护风险。反斜杠后出现空格以外的意外字符，或漏写
某一行的反斜杠，都可能提前结束宏定义。

## include

`#include` 让指定头提供的内容在当前位置参与翻译：

```cpp
#include <vector>
#include "point.h"
```

标准头通常使用尖括号，项目头通常使用双引号；搜索位置与具体实现和编译选项有关。
完整规则见 [#include](include.md)。

一个头可能被多条路径重复包含。传统头文件使用条件编译防止内容重复定义：

```cpp
#ifndef POINT_H
#define POINT_H

struct Point {
    int x;
    int y;
};

#endif
```

第一次包含时 `POINT_H` 尚未定义，正文得以保留并立即定义标志；以后再次包含时，
整个区域被排除。这称为 include guard。

许多编译器还支持 `#pragma once`，但它不是 C++17 标准规定的预处理指令。本仓库
竞赛模板是独立 `.cpp` 文件，不需要维护自定义头和 include guard。

## 宏定义

`#define` 建立对象式宏或函数式宏，`#undef` 取消定义：

```cpp
#define LIMIT 100
#undef LIMIT
```

宏按预处理规则替换记号，没有 C++ 类型。参数括号、重复求值与名称污染等问题见
[#define 宏](define-macros.md)。本仓库不用宏压缩常量、类型、循环或树节点公式。

## 条件编译

预处理器可以根据宏是否存在或整数条件选择代码：

```cpp
#ifdef LOCAL
cerr << "debug\n";
#endif
```

只有定义了 `LOCAL`，中间代码才进入编译。常见条件指令包括：

```text
#if        按预处理整数条件判断
#ifdef     判断宏是否已经定义
#ifndef    判断宏是否尚未定义
#elif      继续判断另一条件
#else      选择剩余分支
#endif     结束条件区域
```

编译命令可以通过选项定义宏，例如 GNU 编译器的 `-DLOCAL`。这属于编译器命令行
接口，不是 C++17 源代码语法。

条件编译与普通 `if` 的差别是阶段：

- `#if` 在编译以前决定哪些记号保留下来；
- `if` 已经是 C++ 程序的一部分，在编译后由程序条件决定运行路径。

若一段被 `#if` 排除，里面的普通语法错误通常也不会被当前构建看到。长期隐藏的
分支因此也需要单独构建和测试。

## 预定义宏

实现会提供一些预定义宏。标准宏 `__cplusplus` 表示当前 C++ 语言标准版本：

```cpp
#if __cplusplus >= 201703L
// 按 C++17 或更新标准编译
#endif
```

编译器、平台和评测系统还可能提供自己的宏。使用它们会让代码依赖对应环境，应先
查平台文档，不要根据宏名字猜测保证。

## pragma

`#pragma` 为实现提供额外控制入口：

```cpp
#pragma once
```

具体 pragma 的含义通常由编译器规定。未知 pragma 的处理也遵循实现规则，因此
不要把某个编译器的优化、打包或警告 pragma 当成跨平台 C++ 语义。

算法竞赛中偶尔能见到用 pragma 强制目标指令集或优化级别的代码。它可能使程序
无法在评测机器运行，也不能修复复杂度不足；本仓库模板不依赖这些指令。

## 查看预处理结果

编译器通常提供只运行预处理的选项。GNU C++ 可以使用：

```text
g++ -std=c++17 -E main.cpp
```

输出可能非常长，因为标准头的内容也被展开。它适合检查宏最终变成了什么、某个
条件分支是否保留，以及头文件从哪里进入翻译单元。

这是 GNU 工具接口，不是程序需要提交给评测机的代码。

## 完整代码

下面用 `LOCAL` 条件宏控制一条调试输出。正常编译只输出答案；使用 GNU 选项
`-DLOCAL` 编译时还会向标准错误流输出输入值：

```cpp
#include <bits/stdc++.h>
using namespace std;

void solve() {
    int a;
    int b;
    cin >> a >> b;

#ifdef LOCAL
    cerr << "a = " << a << ", b = " << b << '\n';
#endif

    cout << a + b << '\n';
}

int main() {
    solve();
    return 0;
}
```

输入：

```text
3 5
```

标准输出：

```text
8
```

无论是否定义 `LOCAL`，算法答案相同；区别只在调试代码有没有进入本次构建。

## 常见错误

### 把预处理指令当成普通语句

指令不写分号，也不遵循函数块中的运行时执行顺序。

### 用条件编译代替运行时分支

`#if` 的条件在构建时决定，不能读取本次程序输入。

### 认为被排除分支已经通过编译

当前构建没有看到的代码不会完成普通语法与类型检查，需要为其他宏组合单独构建。

### 依赖非标准 pragma 修复算法

实现专属优化可能不被评测环境支持，也不会改变错误的渐进复杂度。
