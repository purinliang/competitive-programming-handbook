# Notes 写作与协作规范

本文件约束 `notes/` 下教程正文、知识目录、学习路线和长期图片资产的维护方式。仓库根目录 `AGENTS.md` 的通用约束仍然生效；发生冲突时，以更具体且不违反根规则的本文件为准。

## 模块正文与学习正文

- `catalog.md` 是模块知识注册表，模块正文保存在所属模块目录中，按知识本身组织，适合独立查阅。
- `learning-path.md` 是课程顺序与学习单元的唯一来源。课程需要不同的引入、取舍或练习时，在 `notes/learning-path/<module>/` 建立同名学习正文；尚未迁移的条目可以暂时复用模块正文，逐单元迁移，不批量复制两套相同文件。
- 模块正文和学习正文使用相同的语义文件名作为稳定 `article_key`，但它们是两种出版版本，不要求长期保持逐字一致。共同的 SVG、代码模板和事实定义继续复用，避免复制真正共享的资产。
- 学习路线专属选择题与对应正文并列保存为 `<filename>.quiz.json`。题目属于 Git 中的出版内容；浏览器或未来数据库只保存用户作答状态，不保存题干、选项和解析。
- 单项选择题默认提供四个选项。题量可以用“每个具有独立检验价值的二级标题约一道题”作为审查尺度，但不是机械配额：没有值得检查的新认识时宁可不出题，跨越多个紧密章节的一道综合题也可以替代重复题。
- 正确选项的位置属于题目设计的一部分，写入 Git 后保持稳定，不由前端随机打乱。单篇小测的正确答案应当在 A、B、C、D 之间大致均衡，不能把全部或绝大部分答案机械地放在同一个位置；调整位置时必须同时移动完整选项并重新核对解析，不能为了凑分布损害干扰项质量。

## 标题、单元与扩展命名

- 学习路线中的“学习单元”以下简称“单元”。单元命名一次完整的学习任务，统一使用中文概念，不把 `C++` 关键字、标准库标识符、英文算法名或缩写直接当作单元名。例如使用“类”“标准库基础”“标准库：位集合”，不使用“`class` 与面向对象机制”“基础 STL”“`bitset`”。具体代码拼写由单篇文章负责。
- 第 01–03 章的主题本身已经明确，使用“函数”“复杂度”“标准库基础”等简洁
  单元名，不为整齐机械添加模块前缀。从第 04 章开始，同一章会交错多个知识领域，
  优先使用“知识领域：完整单元名”的形式，例如“数据结构：线性表”
  “数学：数论基础”“图论：树”“动态规划：动态规划基础”
  “字符串：字符串基础”。冒号左侧使用稳定模块，右侧拿掉前缀后仍须是能够独立
  理解的单元名；当模块名本身也是主题名称时允许重复，不把右侧缩成只有依附前缀
  才成立的“基础”。不为表面对称改用“线性结构”“树状结构”等中间形态分类。
- 单篇文章标题必须准确指向一个足够小的主题。已有稳定中文名称的概念只用中文标题，例如“结构体”“联合体”“枚举”“友元”；正文第一次定义时再写“结构体（`struct`）”这类中英文对应，不为了展示关键字把英文机械塞进标题括号。文章直接讲解某个关键字、预处理指令或标准库接口，而且没有自然、通行的中文替代时，标题保留正式源码拼写并使用行内代码，例如“预处理：`#include`”“`vector`”“`pair`”，不把 `vector` 固定翻译成“向量”。中文标题中确实需要出现源码记号时同样使用行内代码，例如“`if` 与 `else`”。
- 数论正文统一使用“质数”和“质因数”，不用“素数”和“素因数”；`primality test`
  统一写作“质数检测”或“质数判定”，不写“素性测试”。旧目录中的人名算法只证明
  曾经接触过该实现，不自动获得独立文章：先抽取它解决的稳定问题，再判断是否需要
  保留通行算法名作为检索词。欧拉、欧几里得、莫比乌斯等已经成为竞赛基础术语的
  名称可以直接使用；冷门人名写法若不能提供独立而长期有效的学习目标，不为追平
  旧模板数量进入近期规划。
- 标题只写文章的上位问题。只为完成该问题而存在的下级机制进入二级或三级标题，不用“与”把它抬成并列主题。例如文章名为“访问权限”，正文下设“友元函数”和“友元类”，不写成“访问权限与 `friend`”。
- 正文标题与目录导航标签可以承担不同职责。正文 H1 保持“欧拉定理”“高斯消元”
  这类聚焦名称；学习路线使用“数学”等粗单元时，表格中的导航标签可以写成
  “数论：欧拉定理”“线性代数：高斯消元”，帮助读者辨认子领域。模块目录已经用
  层级表达所属专题时，不再重复这类前缀。导航标签不能反过来污染正文 H1。
- 学习单元按共同学习目标划分，不按现有文章数量、模块边界或前置依赖机械合并。依赖只决定顺序：二叉堆需要完全二叉树知识，但“二叉树”和“二叉堆与优先队列”解决的问题、维护的不变量和操作不同，因此是两个相邻单元。前缀和与差分、双指针与滑动窗口这类直接的原方法与派生方法可以留在同一单元。
- 模块目录默认使用“模块 → 专题 → 文章”的层级；只有一个专题内部确实已经自然
  分裂出多个稳定家族时，才增加第三级子专题。数学中的数论、组合数学和图论中的
  若干大方向通常需要第三级，线段树、树状数组、并查集等较小而稳定的结构家族则
  可以直接挂文章。Markdown 分别使用 `## 05 数学`、`### 数论` 和
  `#### 专题：筛法与数论函数`；不要为了让所有模块外形相同而强造空洞层级。
- 每个模块都可以设置 `### 常用`，集中列出真正高频、值得反复返回的文章入口。
  “常用”是人工维护的精选入口，不是排他的知识分类：其中的文章仍须同时出现在
  自己所属的正式专题，两个入口共享同一正文身份、评论和进度。“不常用”不作为
  对称分类；低频内容回到其知识专题，并按需要标记为扩展阅读。
- 模块目录不使用“基础”“进阶”作为最高分类依据：这些词会随学习阶段和题目范围
  变化。C++ 模块不再拆成 C++ 基础与 C++ 进阶，而按基本类型、控制流、函数、
  标准库、编译、面向对象等专题组织；数学中数论和组合数学可以作为大专题继续分组，
  矩阵、高精度整数、博弈论等较小方向直接成为专题；数据结构按结构家族组织。
- 动态规划模块的专题名称使用全称并保留模块前缀，例如“动态规划：区间”
  “动态规划：状态压缩”；单篇文章使用竞赛语境中稳定的 `DP` 简称，例如“区间 DP”
  “状态压缩 DP”。不要在专题名中只写“区间 DP”，也不要在文章标题中机械重复
  “动态规划：”。
- 树相关术语不机械统一。“树形 DP”表示状态和转移沿树的递归结构组织，是稳定名称；
  “树上差分”“树上背包”“树上莫队”等表示把某种方法应用到树上。描述形状时使用
  “树形”，描述树上的问题或操作时使用“树上”，不用容易被理解为类型分类的“树型”。
- 专题不表示学习顺序，可以跨越学习阶段聚合同一主题的基础、进阶与扩展文章；同一
  篇正文可以同时属于多个领域、专题乃至模块，此时各入口仍指向同一个稳定正文、
  评论和学习状态。例如矩阵树定理可以同时进入图论的生成树入口与数学的组合计数
  入口，高精度快速乘法可以同时进入高精度整数与多项式卷积入口。无法自然归类的
  交叉主题才进入“其他”，不为消灭“其他”制造错误归属。学习路线仍按真实教学任务
  命名单元，同一正文在确有不同教学用途时也可以拥有多个单元入口。
- 正文身份与导航入口必须分离。评论、已读状态、题目作答和内容修订绑定稳定的 `article_key`、分节 ID 或题目 ID；目录高亮、展开状态、上一篇和下一篇绑定当前导航入口。每个入口至少记录导航模式、章或模块、单元或专题、入口顺序和文章身份。同一正文存在多个专题或单元入口时，目录链接必须携带足以恢复当前入口的上下文；直接访问正文且没有入口上下文时，才使用文档声明的默认入口。不得再用 `article_key` 同时冒充正文身份和唯一目录位置。
- 通常用 3–8 篇短文作为单元边界的审查信号，不把篇数当成硬规则。即使只有一篇，只要已经完成一次独立学习任务，也可以单独成单元；超过八篇时必须重新检查是否混入了多个问题。
- 学习路线的文章 ID 统一使用六位 `CCUUPP`：`CC` 是两位章号，`UU` 是两位单元号，`PP` 是文章在该单元中的两位顺序。例如 `030405` 表示第 03 章第 04 单元的第 05 篇。章、单元和篇序都从 `01` 开始，不使用一位缩写。同一文章有多个导航入口时，ID 只编码权威的主入口，其他入口继续引用同一文章身份。
- 独立扩展和附属扩展都在 ID 前使用 `*`。位于学习路线中的独立扩展仍按主入口获得 `CCUUPP`；不进入学习路线的独立扩展使用保留区 `99MMPP`，其中 `MM` 是模块号，`PP` 是该模块中的扩展顺序。附属扩展共享基础篇的六位 ID 并追加 `e1`、`e2` 等后缀，例如 `*010201e1`。附属扩展不进入学习路线或扩展阅读索引。核心上一篇/下一篇跳过两类扩展，后续核心文章不得把扩展作为必学前置。

- 每篇文章只回答一个足够小的主要问题；不得因为若干概念经常一起教就把它们合并成篇。
- 标题直接描述当前主题，不用“入门：”“基本类型：”“表达式：”“图：”等类别前缀编码导航层级。学习路线由学习单元分组，模块目录由专题分组；标题不再承担分组元数据。只有冒号本身属于通行术语或能表达不可替代的主题关系时才保留。
- 模块正文与学习正文可以使用不同标题；网站分别以 `catalog.md` 和 `learning-path.md` 中登记的标题为准。不要在标题后追加“第一次提交”等仅描述教学任务的副标题。
- 二级标题使用简洁、稳定的名词性短语，使目录可以脱离正文独立阅读；“先……”“再……”“如何……”等口语化过渡留在段落中，不作为标题。
- 行内 Markdown 链接与相邻的中文正文之间各留一个空格；链接紧邻句号、逗号、括号等标点时不在标点内侧额外加空格。
- 知识点独立成篇的条件是：脱离父主题后，它仍有独立的学习目标、语义或模型、使用场景，并值得被下游单独引用。文章很短不是合并理由。
- 只为完成父主题而存在的语法或机制留在父文章中：`break` / `continue` 属于循环，比较器属于排序，迭代器由容器文章解释，函数的形参、实参和返回语法属于函数基础。
- 有依赖不等于应该合篇。例如比较运算产生布尔值，逻辑运算组合布尔值；两者前后依赖，但语义和操作集各自完整，因此分篇。
- `learning-path.md` 的 01–09 按阶段组织核心与当前阶段适合阅读的扩展文章；文末另设“扩展阅读索引”，按模块和 ID 收录可独立查找的扩展专题。学习单元可以同时包含核心与带星文章，核心上一篇/下一篇自动跳过扩展，索引也不表示学习顺序。
- 每个阶段在 `learning-path.md` 中使用“学习单元”组织文章。学习单元是一次相对完整的学习任务，不是按标题、模块或固定篇数机械分组；具有交叉依赖、需要前后对照或共同解决一类问题的文章可以进入同一单元。单元内部仍按前置关系排序，不为标题整齐破坏依赖。
- 学习单元允许螺旋式推进：先建立能够写程序或解题的最小用法，后续单元再回访作用域、表示方式、程序内存或证明。不要为了制造严格线性依赖，把读者尚不需要的底层规则提前倾倒出来。
- 学习单元不替代模块分类。模块目录按知识本质组织，学习路线按教学过程组织；需要不同教学叙事时允许建立学习正文。通常先检查 3–8 篇能否形成自然单元，但篇数只是审查信号：1–2 篇可以独立成单元，超过 8 篇也必须根据学习目标而不是数字决定是否拆分。
- `learning-path.md` 使用 `### 单元 01：名称` 显式分组，单元号始终保留两位。单元号只用于源文件定位、顺序校验和文章 ID，不在网站目录中渲染。整个单元都是扩展阅读时，把标记放在单元名前，写作 `### 单元 06：*类`；网站只显示 `*类`，不再追加“（扩展阅读）”。不要把单元名写进正文文件名或文章标题，避免多处声明失去同步。
- 学习单元按阶段逐步迁移。已经使用显式单元的阶段，其全部文章必须按原顺序恰好属于一个单元；尚未迁移的阶段继续使用原表格和网站的临时专题分组，不为了全局外观一次性猜测所有边界。
- 六位文章 ID 编码权威主入口，不再按模块分配。本次统一迁移后，已登记文章的 ID 和语义路径默认稳定；仅当权威单元或文章边界真正改变时才同步迁移，不为局部排版反复重编号。
- 正文文件名使用小写短横线语义名，直接翻译文章的中文主题，不携带六位 ID、课程前缀或模块前缀。例如“冒泡排序”保存为 `bubble-sort.md`，“最短路：Dijkstra”保存为 `dijkstra.md`。模块正文、学习正文和小测使用同一语义文件名。
- 计划中的知识点只登记路径，不创建空 Markdown 文件。

模块目录的每一行使用固定字段：

```text
ID | 知识点 | 状态 | 文件
```

允许值：

- 六位 `CCUUPP` ID 表示核心教程；ID 前的 `*` 表示独立扩展专题，例如 `*020601`；`e1`、`e2` 等后缀加前缀星号表示基础文章的直接配套扩展，例如 `*010201e1`。`e` 只表达从属关系，不能省略表示扩展属性的星号。
- 状态：`计划`、`推迟`、`待审阅`、`已审阅`。`推迟` 表示知识已经登记，但在可预见
  的较长时间内不进入写作、审核或公开网站；它可以保留尚无正文的代码路径，也可以
  保留已有正文链接。旧文章中的 `草稿`、`定稿` 只作为过渡状态保留；下一次发生
  实质修订时再迁移，不批量伪造历史。
- 正文尚未齐全时不在目录维护前置编号。全书完成到足以观察真实引用以后，再根据正文反向梳理依赖关系。

## 核心与扩展的边界

核心教程解释一个知识点最常用、最基础、足以独立解决标准问题的版本，并说明代码每个组成部分为什么存在。

例如：

- 树状数组正文解释 `lowbit`、节点覆盖区间、`add` 与 `prefix_sum` 的跳转及区间和。
- 线段树正文解释递归划分、`4n` 空间、`build/pull/push`、基础查询修改和一种基础懒标记。
- 普通图正文展示结构本身的 value 与边关系，不把内部 id 当成教学重点。

某篇文章适合在当前阶段学习、跳过又不会阻塞后续，而且只在少数题目、考试或读代码时使用时，通常标记为扩展。扩展表示学习路线中的可选分支，不表示文章没有价值、没有结构或必须被扔到全书最后。

以下内容通常独立为扩展专题：

- 为少见功能精密改造基础结构，例如树状数组维护区间最值。
- 需要额外技巧但不改变基础结构理解的操作，例如线段树二分。
- 复杂标记组合、可持久化、动态开点、Segment Tree Beats 等高级变体。
- 左偏堆、复杂平衡树、高级字符串结构等低频或超出主路线收益范围的内容。

独立扩展专题必须进入模块目录和路线文末的扩展阅读索引；若能判断适合阅读的阶段，还应进入该阶段下主题明确的学习单元。不能把多个无关主题塞进一个笼统的“扩展阅读”单元，也不能让带星文章成为核心主线的必学前置。附属扩展仍在 `catalog.md` 注册稳定身份并由模块目录收录，同时从基础文章按真实关系链接；后续核心教程必须允许读者跳过全部扩展继续学习。

标准库教程只负责容器或固定任务的接口、常用复杂度和比赛所需的最少安全规则，不在同一篇重新推导底层数据结构。不设“STL 算法大全”、“比较器”或“迭代器”这种泛化主线文章：比较器放在排序文章中，迭代器由各容器文章在首次使用时解释。迭代器失效不单独成篇，也不罗列完整标准表；相关教程只需展示遍历中用 `it = container.erase(it)` 删除的安全模式，并提醒 `vector` 扩容后旧迭代器、指针和引用不能继续使用。

标准库文章不能退化成接口清单。读者已经学过对应结构或算法时，正文必须说明标准库封装了哪些手写操作、保持了什么语义、复杂度如何，以及它能替代前文哪一种写法；同时指出这种替代失去了哪些控制能力或增加了什么限制。标准库没有承诺的底层实现只作为理解常见行为的注释，不为了会调用接口而提前教授红黑树、哈希冲突工程或其他复杂实现。

能够替代前面算法的便利工具通常不是那些算法的前置。例如有序关联容器应当放在排序和二分以后，用来比较“静态排序后查询”和“动态维持有序集合”；不能先让 `set` 解决全部问题，再把排序与二分写成失去动机的底层知识。`vector`、`string` 等会被后续代码普遍依赖的基础表示可以按真实需要提前学习，但也要与数组、C 字符串或对应操作成本建立联系，而不是孤立背诵 API。

抽象数据结构和标准库实现必须分篇：数组、链表、栈、队列、二叉堆和哈希表负责结构、操作与复杂度；`vector`、`stack`、`queue`、`priority_queue` 和无序关联容器负责比赛中的编码接口。不能因为比赛中通常直接调用标准库，就省略结构本身，也不能在概念文章中顺便教完容器接口。`vector`、`string` 和 `sort` 等最低限度工具可以先作为接口使用，学习复杂度后再从数据结构或算法视角重新理解；`stack`、`queue`、`priority_queue` 等名称直接对应抽象结构的工具，则先讲概念，再紧邻安排接口文章。

C/C++ 核心语言层的概念通常已经有稳定中文名，例如结构体、联合体、枚举、指针、引用和类；标准库的具体类型和函数通常直接使用源码标识符更自然，例如 `vector`、`pair`、`sort` 和 `push_back`，不创造会替代正式名称的固定中文译名。中文正文负责解释它们的语义，例如“使用 `struct` 声明结构体类型”“`vector` 是动态数组式的序列容器”。标准库中已经稳定的上位概念仍使用中文，例如容器、迭代器、算法、关联容器、结构化绑定和容器适配器。单篇标题按本文件的标题规则选择纯中文概念名或带行内代码的正式标识符，所属知识领域由学习单元和模块专题表达。不得把 `vector` 固定译为“向量”，以免与数学和计算几何中的向量混淆。

抽象数据结构使用中文名称，例如栈、队列和优先队列；`stack`、`queue` 和 `priority_queue` 则专指 C++ 标准库提供的具体类型。正文不得用标准库类型名替代抽象结构，也不得把“优先队列”写成 `priority_queue` 的专属中文译名：其他实现同样可以满足优先队列的抽象接口。

课程中的“标准库基础”收录后续代码立即依赖的少量类型与算法，“标准库进阶”收录在掌握相应数据结构和复杂度以后才选择的 `priority_queue`、有序关联容器与无序关联容器。“进阶”描述课程顺序，不表示这些接口罕见或实现困难。GNU PBDS 等非标准扩展不得混入标准库单元，只作为明确标星的独立扩展阅读。

算法与数学名称按中文竞赛圈的稳定通名处理。中文资料也普遍直接使用拉丁字母的人名算法保留原名，例如 `Kruskal`、`Bellman–Ford`、`Floyd–Warshall`、`Dijkstra`、`Hierholzer`、`Tarjan` 和 `Dinic`，不使用生硬音译；已经形成固定中文名称的概念使用中文，例如欧拉函数、莫比乌斯函数、欧拉路径、欧拉回路、欧拉图、哈密顿路径和哈密顿图。描述性名称使用中文，并在首次出现时给出通行缩写，例如深度优先搜索（DFS）和广度优先搜索（BFS）。

二进制二选一模型统一写作 `0-1`，使用短横线：`0-1 背包`、`0-1 BFS`。标题和正文不交替使用 `01`、`0/1` 等写法。

## 图论术语

- 中文术语以 [OI Wiki](https://oi-wiki.org/graph/concept/) 的竞赛用法为基准；英文竞赛术语以 USACO 收录的 [Competitive Programmer's Handbook](https://usaco.guide/CPH.pdf) 为基准。其他教材中的别名只在确有必要时放入引用块，不在正文中交替使用。
- Breadth-first search 统一译为“广度优先搜索（BFS）”；“宽度优先搜索”只在辨析别名时出现。无向图的 maximal connected subgraph 统一称为“连通分量”；“连通块”可以在首次定义时注明为竞赛口语，标题、目录和后续正文不再交替使用。
- 一般图的对象首次出现时写“顶点（vertex），简称点”，此后正文只使用竞赛中更常见的“点”；相应地使用“点集、点数、点权”等说法。进入树的语境后统一使用“节点”，例如根节点、父节点、子节点和叶节点；说明树与图的对应关系时，可以明确写“树的节点对应图中的点”。链表等由实体组成的数据结构也沿用“节点”。英文图论资料即使使用 node，中文的一般图正文仍写“点”。
- `path` 统一译为“路径”，指点不重复的边序列；`cycle` 统一译为“环”，指除首尾重合外不重复点的闭合结构；`self-loop` 或 `loop` 统一译为“自环”。
- `circuit` 统一译为“回路”，指边不重复、但允许重复经过点的闭合结构。基础概念正文不展开 `walk`、`trail` 与 `circuit` 的完整分类，只在自环、欧拉或哈密顿语境中解释真正需要的区别。
- 固定使用“欧拉路径（Eulerian path）”“欧拉回路（Eulerian circuit）”“哈密顿路径（Hamiltonian path）”“哈密顿回路（Hamiltonian circuit）”和“有向无环图（Directed Acyclic Graph，DAG）”。其他中英文名称只作为注释。
- 题面若自行定义 path、cycle 等词，以题面定义为准；教程应直接复述“是否允许重复顶点或边”，不要只依赖术语猜测限制。
- 教程正文、示例代码和图示中的点编号统一使用从 `1` 开始的连续整数 `1, 2, ..., n`，不使用字母充当点编号；YAML 中的图节点 `id` 与该编号保持一致。点权是附在点上的独立数值，不能代替点编号。
- 图的基础存储示例使用 `graph`、`from`、`to`、`weight` 等完整名称说明每个量的含义；进入可复制的竞赛代码后，统一使用常见缩写 `g`、`u`、`v`、`w`。布尔邻接矩阵命名为 `connected`，带权矩阵命名为 `weight`，不使用无法体现格子含义的二维 `graph`。
- 图的三种基础存储方式统一称为“边集、邻接矩阵、邻接表”。“邻接表”描述的是为每个点保存出边集合的抽象方法，不限定底层容器；`vector` 邻接表、前向星和链式前向星都是邻接表的实现。“邻接链表”只在底层确实使用链表时出现，不作为 adjacency list 的统一译名。
- 普通图算法的主线模板只使用 `vector` 实现邻接表。对应文章标题写作“图的存储：邻接表（vector 实现）”，正文在语境明确后可以简称“`vector` 邻接表”。无权邻接项保存 `int`；带权邻接项优先保存 `pair<int, int>`，固定按 `(to, weight)` 排列，并用 C++17 结构化绑定 `for (auto& [v, w] : g[u])` 访问。边集在需要整体扫描或排序全部边时独立成篇；邻接矩阵也独立成篇，解释无权、有权、有向和无向图的矩阵表示、$O(n^2)$ 空间及 $O(1)$ 判边。后续算法仍按题目语义选择合适表示，不把邻接矩阵误写成普通稀疏图的默认模板。
- 前向星是将边集按起点分组后，用每个点的区间边界定位连续出边；常见排序构建为 $O(m\log m)$，计数分组也可达到 $O(n+m)$。它只用于解释存储关系，不列入主线模板。
- 欧拉图、网络流等高频访问配对反向边的算法改用链式前向星：两条记录连续存入全局边数组，以 `edge_id ^ 1` 互相定位，并可用 `head` 或当前边下标跳过已经无用的记录。对应文章标题写作“图的存储：邻接表（链式前向星实现）”。链式前向星在高中阶段独立成篇，作为邻接表的特殊数组实现教授，不列为第四种基础存图方法。哈密顿问题限制的是点而非边，不因此改用链式前向星。

树位于图论与数据结构的交界，模块归属不能只按“是否有根”或“是否称为节点”判断：

- 当题目给出一棵树，我们研究它的点边关系、路径、遍历、直径、重心、LCA 或分治时，归入图论；临时选根只是为无向树赋予父子层级。
- 当树形由我们为存储数据和支持操作而构造，并需要维护左右孩子、键值顺序、区间、平衡性等不变量时，归入数据结构，例如二叉搜索树、堆、线段树和平衡树。
- 普通二叉树兼有两种视角。本书把显式左右孩子、存储方式及前序、中序、后序遍历放在数据结构模块；把不依赖左右次序的树上遍历与性质放在图论模块。
- 树的基础概念先讲无根树，再讲指定根以后新增的层级关系。无根树的叶节点定义为度数不超过 `1` 的节点，以覆盖单节点树；有根树的叶节点定义为没有子节点的节点，因此只要根有子节点，它就不是叶节点。

## 文章信息块

文章没有永远不再修改的“终稿”。状态只描述当前版本是否经过用户完整审阅：

- `计划`：目录中已有节点，但尚无正文。
- `推迟`：目录中保留身份和分类，但当前不写、不审，也不进入公开网站的目录、搜索、
  统计或正文路由。恢复工作时先改回 `计划`、`待审阅` 或 `已审阅`。
- `待审阅`：正文已经存在，但用户尚未完整审阅当前版本。
- `已审阅`：用户已经完整审阅当前版本；这不妨碍文章以后继续修订。

新文章必须在一级标题后用一行记录最近修订时间和审阅状态，使用 Australia/Sydney 当时的 UTC 偏移：

```markdown
# 树状数组：基础

> 最近修订：2026-08-13 14:30 +10:00（未审阅）
```

要求：

- 信息块括号中的审阅状态必须与 `catalog.md` 一致：`未审阅` 对应 `待审阅`，`已审阅` 对应 `已审阅`。核心或扩展属性只在目录 ID 上标记。
- 正文可以在真正有帮助时用自然语言链接前置阅读，但不维护编号化的强制前置清单。
- 新正文一律从 `待审阅` 开始，信息块写“未审阅”。只有用户明确表示已经完整审阅当前版本，才能把目录改为 `已审阅`，并把括号改为“已审阅”；局部批注、讨论某一节或 agent 自检不算完整审阅。
- 教学内容、代码、示例、标题或章节结构发生实质变化时，更新“最近修订”。若文章原为 `已审阅`，将目录改回 `待审阅`，并把括号改回“未审阅”。
- 纯格式化、拼写、链接或 LaTeX 兼容性修复不更新文章日期，也不改变审阅状态。
- 旧文章中的 `草稿`、`定稿` 和简短信息块不批量迁移。下一次实质修订该文时，再改用新状态并写入当次“最近修订”，不得猜测或倒推历史日期。
- 信息块固定写作 `> 最近修订：YYYY-MM-DD HH:MM +HH:MM（未审阅）` 或对应的负 UTC 偏移、已审阅状态。不记录初稿时间，也不单独记录审阅时间。
- 已有正文的二级标题视为稳定引用接口。重命名时检查并更新所有下游锚点链接。

## 正文内容检查清单

下面八项是写作时逐项判断的内容清单，不是固定目录。文章只保留真正有教学价值的部分，可以改标题、调整顺序或合并相邻内容；不适用的部分直接省略，禁止为了结构齐全制造空洞章节。

1. **问题背景**：为什么要引入这个知识点，它解决什么困难。算法文章通常从直接或暴力解法的时间、空间或实现问题出发；语言和工具文章只需说明真实用途，不必虚构“暴力解法”。
   算法文章必须优先回答它能够优雅地解决什么问题。代表题的限制应该来自问题
   本身的自然结构，而不是为了排除其他算法，人为叠加一串无关限制，硬造出
   “只能使用本文算法”的场景。一道好的代表题应该让算法的状态、不变量或
   复杂度优势自然出现。
2. **前置知识**：只在读者确实需要复习或跳转时，用自然语言说明理解正文所需的背景；不为计划中的文章维护编号化依赖。
3. **逐步解构与图示**：从读者已经理解的做法出发，逐步增加真正需要的结构。先让读者看见为什么需要区分或保存一个东西，再给它准确、稳定的中文名称和英文代码名；不得开头集中倾倒变量、数组和函数定义。手算、流程图或 SVG 只在能显著帮助理解状态变化时使用。
4. **示例代码**：把已经讨论清楚的方法逐块翻译成 C++17，每块代码对应一个明确步骤。不得在代码中突然加入正文没有出现的优化、状态或抽象。
5. **完整代码**：当本文得到一个可以独立运行或提交的程序、算法或数据结构实现时，在正文内完整复制，不用模板文件、其他笔记或外部链接代替。若知识点本来只有局部语法或接口，则提供足以说明它的最小完整示例，不强行拼成大程序。
6. **基础练习**：只选择使用本文及其直接或传递前置就能完成的题目。若一个短小的语法或接口主题没有值得单列的练习，可以省略；不得用尚未学习的技巧凑题单。
7. **扩展阅读**：只登记自然延伸但不属于基础版本的未来工作。没有合适内容时省略。著名不等于适合现在学习；扩展阅读不是下一课。
8. **需要记住什么**：每篇核心知识正文在末尾用自检问题指出当前真正需要掌握的内容，并明确哪些细节只需理解或能够查阅，不要求背诵。问题必须能够只依靠本文及其前置回答，不提供参考答案，也不能用新的术语考查正文没有教过的内容；读者答不上来时应返回对应章节复习。配套扩展篇根据用途明确掌握边界：课程或考试会涉及的内容同样设置自检问题；纯背景与查阅内容则明确说明不要求任何读者理解或记忆，不设置变相的必答问题。路线说明等不承担知识教学的文档可以省略。

主学习路线的上一篇、下一篇和学习单元由网站统一生成，正文不维护“上一篇”“下一篇”等低信息导航章节。正文需要引用其他文章时必须说明实际关系并写明文章名称，例如“这条性质将在……中使用”或“更完整的表示方式见……”，不能依赖读者当前的阅读顺序猜测目标。

基础篇与其客观配套的深入篇可以保留人工双向链接，但标题必须描述关系，例如“配套深入篇”“返回基础篇”，不能把扩展篇伪装成路线中的普通下一课。已有“下一篇”章节在文章下一次修订时删除；若其中包含有价值的知识承接，则改写到相关正文段落或扩展阅读中，不做无差别文字删除。

算法和数据结构文章通常需要完整覆盖背景、推导、正确性直觉、复杂度、关键边界、分块代码、完整实现和基础练习。C++ 语法、STL 接口、路线导读和短参考应按主题自然展开：给读者当前需要的用途、最小示例、语义、常用复杂度与陷阱即可，不套用算法文章的外形。常见错误和可操作的调试方法应紧邻相关内容出现。

代码继续遵守仓库约定：竞赛风 C++17；需要标准库、命名空间、`long long` 别名或输入输出时，分别使用 `#include <bits/stdc++.h>`、`using namespace std;`、`typedef long long ll;` 和 `scanf` / `printf`。第一次接触完整程序时可以使用更直观的 `cin` / `cout`，避免同时引入格式控制符；这不改变后续竞赛代码的默认约定。最小示例不添加没有被正文动机引出的固定行。代码命名应与解释保持一致。

命名空间与 `struct`、`class` 使用同样的 4 空格内部缩进，由根目录 `.clang-format` 中的 `NamespaceIndentation: All` 统一检查。命名空间没有 `public` 和 `private` 访问权限；对外入口与内部辅助函数依靠命名、局部作用域和正文说明区分，不为模拟类的访问控制增加空壳封装。

教程正文和可复制的竞赛模板使用竞赛圈常见的简洁转换写法，不使用冗长的 `static_cast`。题面上限保证长度能放进 `int` 时，直接写 `int n = strlen(s);` 或 `int n = s.size();`；需要在整数除法前进入浮点运算时优先写 `1.0 * sum / count`，确实要明确目标类型时使用 `(int)x`、`(double)x` 等常见写法。验证程序等仓库内部工具不受此展示风格约束。

多个返回值天然组成一个结果时，优先直接返回 `pair` 或专门的 `struct`，不要使用 `bool` 加多个输出引用参数模拟返回值。只有两个值且含义已经由函数名和正文解释清楚时使用 `pair`；若合法结果存在不会冲突的哨兵，可以统一返回哨兵表示失败，并在正文说明判断方式。

容量上限常量使用 `MAXN`、`MAXM` 等 `MAX` 前缀名称，实际输入规模使用小写 `n`、`m`，不得用单独的 `N` 同时表示容量和实际长度。竞赛代码中的十进制整数量级可以写成 `1e5 + 5`、`2e5 + 5`；派生容量优先直接表达关系，例如无向边的两条记录可写为 `const int MAXM = 2 * MAXN`，线段树数组可写为 `tree[4 * MAXN]`。

基础文章优先给出一个最常见实现。不要为了覆盖所有题型把模板抽象成复杂框架；题目特有胶水、罕见维护信息和高级优化应进入扩展专题、模板验证入口或工作区。

题目给出稳定规模上界时，一次性竞赛代码的数值状态默认使用全局定长数组，容量常量本身已包含余量，例如 `const int MAXN = 1e6 + 5;`。线段树等需要常数倍节点的结构直接表达推导关系，例如 `tree[4 * MAXN]`；不把算法明确需要的倍数空间误当成 `+5` 边界余量。大型临时数组只在一个函数中使用时，声明为该函数的局部 `static` 数组：它们位于静态存储区，但名称不泄漏到函数之外。

数据结构需要绑定状态与操作时仍优先使用 `struct`，并将实例放在不会占用大量调用栈的作用域。只有长度只能在运行时确定、同时需要多个不同规模的实例、频繁改变长度，或固定容量会造成真实的常数倍内存压力时，才改用按实际规模分配的 `vector`。后缀自动机、可持久化数据结构等空间常数较大的算法必须单独推导容量，不机械套用默认。

空间取舍默认优先语义明确、约定一致和降低越界风险。允许用 `0` 号哨兵、`+5` 余量或其他少量额外空间换取更稳定的统一写法，不为了节省几个元素破坏语义；只有题目的内存限制确实让常数倍成为瓶颈时，才针对该题偏离默认约定，并说明原因和新的边界。

是否使用 `struct` 取决于状态和操作是否构成一个对象：数据结构的多个操作共同维护一份持续状态时，使用 `struct` 绑定状态与方法，例如树状数组、线段树、并查集和平衡树；一组算法使用题目级共享输入并且通常只构造一份结果时，可以使用命名空间集中名称，例如后缀数组；计算只依赖本次参数且没有跨调用状态时，使用普通自由函数，例如 `gcd`、`exgcd`、快速幂、单次 CRT / exCRT 和质数判断。数学对象本身拥有值与封闭运算规则时仍可使用 `struct`，例如 `modint`、矩阵和多项式。不为形式统一把一组无状态函数塞进空壳对象。

### 下标约定

- 长度为 `n` 的自定义数组、同余方程组等线性对象使用 `1..n`；图和树的点、节点默认也使用 `1..n`。位置 `0` 留给空前缀、空节点、边界或哨兵，不存放正文中的第一个真实元素；
- 原生 `string` 的字符位置使用 `0..n - 1`，以便直接使用 `size()`、拼接、比较和 `substr()`。后缀数组、后缀自动机等自定义结构的逻辑位置或状态继续使用 `1..n`；访问原生字符时，逻辑位置 `pos` 映射到 `s[pos - 1]`。正文的数学说明必须与它所描述的代码对象使用同一套下标；
- 主线字符串算法在没有其他题面条件时，默认输入只包含小写拉丁字母 `a` 到 `z`。这是每篇代码必须明示的输入契约，不把算法本身误说成只能处理 26 个字符；文章的目标本来就是 ASCII、大小写或任意字节时除外；
- 题目上界已知时，自定义数值存储使用已包含余量的 `MAXN`、`MAXM` 和全局定长数组，不在每个容器分配处重复写 `n + 5`。只能动态分配时，按真实需要分配 `n + 1` 或算法明确推导出的更大容量，不用 `+5` 替代边界证明；
- 教程中的动态 0-1 标记数组默认使用 `vector<int>` 和数值 `0`、`1`，不用具有
  特殊压位语义的 `vector<bool>`。这与其他 `vector` 保持相同的元素访问行为，也
  符合用少量空间换取清楚语义的取舍；只有内存限制确实构成瓶颈时才改用
  `vector<char>` 等紧凑存储，并在正文说明原因。验证工具不受此展示规则约束；
- 只有在直接讲解或调用 C++ / STL 的原生接口时，才保持它们的自然约定：原生数组、`string` 和 `vector` 下标从 `0` 开始，迭代器区间通常左闭右开。具体接口若使用位置加长度等其他规则，按标准库的真实语义说明；
- 题面或 STL 接口与本书自定义表示不一致时，只在输入、输出或调用边界集中转换，并立即注明转换。转换完成后回到本书的 1-based 与闭区间约定。

### 区间约定

- 数学说明、函数接口和自定义题目操作默认使用闭区间 `[l, r]`，长度为 `r - l + 1`。原生 `string` 上的直接讲解可以使用 0-based 闭区间 `s[l..r]`；自定义字符串结构中使用的 `s[l..r]` 则按文章已声明的 1-based 逻辑位置解释；
- 只有在直接讲解或调用 C++ / STL 的原生接口时，才保持它们的自然约定：迭代器区间通常左闭右开，具体接口若使用位置加长度等其他规则，按标准库的真实语义说明；
- 题面或 STL 接口与本书自定义表示不一致时，只在输入、输出或调用边界集中转换，并立即注明转换。不在同一段推导中无说明地混用闭区间与左闭右开区间。

## 引用与复用

- 下游文章不重复讲解已经稳定成文的基础，只做一句必要提醒并链接到对应小节。
- 正文可以引用已经存在的核心教程或扩展专题；引用只表达实际需要，不建立一套尚需持续维护的目录级依赖图。
- 允许从任意节点开始起草；提交正文前检查实际引用是否足以让目标读者继续阅读。
- 若 `已审阅` 或旧 `定稿` 文章需要实质修改，先检查下游引用；完成修改后标为 `待审阅` 并更新修订时间，等待用户再次审阅。

## SVG 图示

- 教程只引用 SVG，不创建或引用 PNG。
- 新图的 YAML 源保存在 `tools/diagrams/sources/<module>/`。
- 长期引用的 SVG 保存在 `notes/assets/<module>/`，并与 YAML 使用相同 basename。
- 已存在于 `tools/diagrams/examples/` 的正式示例可以继续作为对应 SVG 的来源。
- YAML 只描述结构与语义，不保存坐标、字体、线宽或具体色值。
- 提交前验证 YAML、重新渲染 SVG，并检查图片链接与文字可读性。

## 逐篇协作状态机

默认一次只主动推进一篇教程：

1. 从学习路线或模块目录选择一个节点。
2. Agent 起草正文、必要 YAML/SVG，并同步目录状态。
3. 运行 `make notes-check` 和相关代码/图示检查。
4. 只提交该文章、直接资产和必要导航变化，提交信息为 `notes: 起草……`。
5. 用户补充细节或提出问题；Agent 先解释，再按要求修订并使用 `notes: 修订……` 提交。
6. 只有用户明确表示已经完整审阅当前版本，才把状态改为 `已审阅`，把信息块括号改为“已审阅”，并使用 `notes: 标记……已审阅` 提交；最近修订时间保持不变。
7. 审阅不是冻结。文章以后仍可修订；发生实质修改时重新标为 `待审阅`。
8. 下游文章可以引用已经存在且内容足够稳定的具体章节，不要求前置文章拥有不可变的终态。

用户授权全库自动起草时，仍然保持上述“一篇正文、一次检查、一个提交”的粒度，不把多篇草稿压进一个提交。默认先按 `learning-path.md` 完成全部核心教程，再按 `catalog.md` 的模块与 ID 顺序完成扩展专题；写作过程中发现主题边界、难度或顺序不合理时，可以同步修订大纲后继续，不等待大纲成为不可变的最终版本。起草正文或补充 takeaway 题目触及某篇文章时，可以逐篇修正聚焦不准的标题，并把它接入或移动到由若干短文组成的显式学习单元；通常检查 3–8 篇能否组成完整任务，但不为凑数量破坏依赖。

全库自动起草时不为每篇文章重复运行整站内容编译或全量构建。逐篇阶段
只做 Markdown、JSON、链接和代码片段所需的轻量检查；累积一个自然批次后再运行
目录全量校验和网站增量内容编译，部署前才运行必要的整站构建。

不得把其他已暂存或未跟踪的 notes 改动混入当前文章提交。提交前使用精确路径检查和提交；不执行破坏性 Git 操作清理用户工作区。

## 大纲维护

- 进行章节、单元、专题、文章边界或学习顺序调整时，先阅读
  `docs/curriculum.md`；它是当前课程结构的最高依据。逐篇迁移和缺篇清单见
  `docs/curriculum-remediation.md`。不再保留会与当前决策竞争的历史课程目标。
- 第 01–03 章当前正按 `docs/curriculum.md` 重新建立真实单元边界；在迁移
  完成前不得把旧目录当作稳定基线。迁移完成以后仍按正文暴露出的具体教学问题小步
  调整，不为名称对仗、数量整齐或一次性完成分类而批量重排。
- 新知识点先进入 `catalog.md`，确定类型、路径和模块 ID。
- 核心教程随后插入 `learning-path.md` 的合适教学位置；独立扩展专题必须加入文末“扩展阅读索引”，能够判断适合阶段时再加入对应学习单元。附属扩展不进入学习路线或扩展阅读索引，但保留在模块目录。
- 学习路线目标是从 C++ 基础到约 Codeforces 2100 的高频、通用知识，不按单题 rating 机械裁切。
- 学习路线中的“C++ 基础”只表示继续学习算法所需的核心语言能力，不冒充完整的计算机组成、体系结构或编译原理课程；不阻塞主线的语言机制独立放入 `02 C++ 进阶`，并保持可跳过。
- 学习路线的层级不是模块隔离墙。`03 算法入门` 先建立复杂度、算法设计思想和必要
  的标准库基础，再学习前缀和、排序、二分、离散化和双指针等第一批基础算法；
  具体枚举、完整贪心、基础数据结构及其标准库接口从 `04 初中基础` 开始按真实依赖
  展开。链表合并和环形链表快慢指针依赖链表，只作为双指针单元的后向扩展。
- 难度阶段固定使用“初中基础、初中进阶、高中基础、高中进阶”，不使用“经典中级算法”等边界不清的自造层级。
- `06 高中基础` 以高中组中争取约 150–200 分所需的高收益主干为筛选尺度，不能把
  “高中阶段能够学习”误当成进入本章的理由；`07 高中进阶` 再收纳依赖更完整、收益
  更专门的模型。第 06–07 章默认使用算法基础、数据结构、数学、图论、动态规划、
  字符串和计算几何等较粗单元；树、最短路、最小生成树等边界稳定且内部确有连续
  前置关系的算法家族可以独立成单元。
- 学校竞赛主线到 `07 高中进阶`；`08 区域赛银牌` 和 `09 区域赛金牌` 继续按真实
  区域赛能力组织。长期没有教学收益的争冠资料不建立第 10 章，只在模块目录中保留
  “推迟”身份。扩展阅读可能明显超过当前阶段，不暗示统一难度或严格先后顺序。
- `learning-path.md` 的扩展阅读索引必须覆盖 `catalog.md` 中每个独立 `*` 节点，不收录带 `e` 的附属扩展；索引先按模块、再按 ID 排列。
- 数学、图论、数据结构等分支可以处于同一阶段；路线只维护明显合理的先后，不在正文完成前假装拥有精确拓扑序。
- 修改目录后必须运行 `make notes-check`。
- 已发布文章的目录 ID 和全局顺序默认保持稳定。新增或拆分单篇正文时，不为了保持
  编号连续而顺延同组的全部既有 ID；允许展示顺序与 ID 暂时不连续。只有积累了多项
  明确的单元、专题或编号调整，并由用户启动集中目录治理批次时，才统一重编号和修改
  全局导航。网站当前会把目录与上一篇、下一篇信息写入大量静态页面，这类全局修改会
  使大批构建产物失效，因此不与普通正文修订混在一次部署中。
