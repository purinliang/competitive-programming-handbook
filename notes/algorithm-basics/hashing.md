# 哈希

> 最近修订：2026-08-17 01:54 +10:00（未审阅）

程序有时要把范围巨大或结构复杂的对象转换成一个固定范围内的整数：根据用户编号选择存储桶、给状态生成快速指纹，或者把字符串映射成便于比较的数值。

完成这种映射的函数称为**哈希函数**（hash function），产生的结果称为哈希值。本篇只讨论映射、冲突与分布；[哈希表](hash-table.md)会使用这些性质实现增删查。

## 从大范围映射到小范围

设键的范围很大，而程序只有 `bucket_count` 个桶。哈希函数把键 `key` 映射到有限输出：

$$
h(key)\in\{0,1,\ldots,B-1\},
$$

其中 $B$ 是桶数。

最简单的整数示例是取模：

$$
h(key)=key\bmod B.
$$

当 $B=7$ 时：

| 键 | 哈希值 |
| ---: | ---: |
| `3` | `3` |
| `10` | `3` |
| `16` | `2` |

哈希不是排序，也不是无损压缩。得到哈希值 `3` 以后，无法唯一判断原键是 `3`、`10` 还是其他同余整数。

## 相等键必须得到相同结果

一个可重复使用的哈希函数必须满足：只要两个键按照题目定义相等，它们就得到相同哈希值。

$$
x=y\implies h(x)=h(y).
$$

否则，插入时把键放入一个位置，查询同一个键时却去另一个位置，就永远找不到原记录。

反命题不成立：

$$
h(x)=h(y)
$$

不能推出 $x=y$。不同键得到相同哈希值是正常且必须处理的情况。

对结构体键，自定义“相等”与“哈希”必须使用一致字段。例如选手记录若只按 `id` 判断相等，哈希也必须只由 `id` 决定；不能让两个相同 `id` 因姓名不同得到不同哈希。

## 哈希冲突必然存在

不同键映射到同一个哈希值，称为**哈希冲突**（hash collision）。

若可能的键数量多于哈希输出数量，根据抽屉原理，必然至少有两个不同键进入同一个输出位置。不存在一种把无限整数无冲突地映射到固定数量桶的普通哈希函数。

因此，正确目标不是“保证永远没有冲突”，而是：

1. 让普通输入尽量均匀分散；
2. 在冲突发生时仍能比较完整键并得到正确结果；
3. 评估恶意或极端输入是否会让性能退化。

哈希表会使用拉链法或开放寻址处理冲突。字符串哈希若只比较哈希值，则通常只能把冲突概率压低，或在需要绝对正确时再验证原字符串。

## 分布为什么重要

假设有 $B$ 个桶和 $n$ 个键。理想情况下，各桶元素数量大致接近 $n/B$。

若哈希函数只保留输入中本来就缺少变化的部分，很多键会集中到少量桶。例如输入全部是 `7` 的倍数，而桶数也是 `7`：

$$
h(key)=key\bmod7
$$

会让所有键进入桶 `0`。

平均桶长不再能代表真实查询成本：空桶很多，唯一拥挤的桶可能需要线性扫描。

好的分布依赖键的结构和输入来源。一个函数对随机整数表现均匀，不代表面对人为构造输入仍然安全。

## 碰撞概率

假设哈希值近似独立、均匀地分布在 $H$ 个可能结果中。放入 $k$ 个不同键时，任意一对键发生冲突的概率是 $1/H$，键对数量为：

$$
\binom{k}{2}=\frac{k(k-1)}2.
$$

当总体冲突概率仍较小时，可以用：

$$
\frac{k(k-1)}{2H}
$$

粗略估计“至少出现一次冲突”的概率量级。

这体现了生日悖论：不是等到 $k$ 接近 $H$ 才容易冲突，而是当 $k$ 接近 $\sqrt H$ 时，冲突就已经不可忽略。

例如 32 位哈希约有 $2^{32}$ 个结果，只处理几万个不同对象时，碰撞风险就可能进入需要认真考虑的范围。使用两个独立哈希或更宽的 64 位输出能显著降低普通随机碰撞概率，但不能把“概率极低”写成数学上的“不可能”。

这套概率估计建立在近似均匀、独立的假设上。若哈希函数或输入存在规律，真实冲突可能远高于公式。

## 桶编号与哈希值

哈希函数可以先产生较宽的整数值，再根据当前桶数得到桶编号：

```cpp
size_t hash_value = hash<Key>()(key);
size_t bucket_index = hash_value % bucket_count;
```

两者不是同一个概念：

- 哈希值由键和哈希函数决定；
- 桶编号还取决于当前桶数；
- 哈希表扩容后桶数改变，同一键可能进入新桶，因此需要重新哈希。

本篇教学代码为了直接观察分布，让取模结果同时充当哈希值和桶编号。

## 负数取模

C++ 的负数 `%` 结果可能为负，不能直接当数组下标：

```cpp
ll remainder = key % bucket_count;

if (remainder < 0) {
    remainder += bucket_count;
}
```

此时 `remainder` 位于 `0..bucket_count-1`。本书自定义桶数组使用 1-based 下标，再加 `1`：

```cpp
int index = remainder + 1;
```

归一化只是把数学同余类放入合法下标范围，不会消除冲突。

## 常见构造思路

哈希函数通常会组合以下操作：

- 取模或截取固定位宽，让结果落入有限范围；
- 乘以常数再加常数，打散简单的等差结构；
- 移位和异或，让高位信息影响低位；
- 多轮混合，使输入的一小处变化扩散到多个输出位。

例如线性形式：

$$
h(x)=(ax+b)\bmod p
$$

可以在选择合适参数时改变简单取模的分布。平方取中、折叠若干数位等方法也常出现在入门资料中，用于说明“从键中提取并混合信息”的想法。

这些名称不是通用安全保证。固定参数和简单混合可能被构造输入针对；整数乘法还要处理溢出。竞赛代码若标准库哈希已经满足需求，应优先使用标准实现；只有输入可能攻击哈希或键类型没有默认哈希时，再选择经过验证的自定义方案。

## 字符串哈希的位置

字符串哈希需要把字符顺序逐步合并，并处理子串哈希、幂次和模数等结构。它依赖字符串概念，也服务于字符串匹配，所以属于字符串专题。

本篇只建立所有哈希共同使用的映射、冲突和概率语言，不把字符串算法塞进整数哈希示例。

## 完整代码

下面读入 `n` 个保证互不相同的 64 位整数，用取模映射到 `bucket_count` 个桶，并统计发生冲突的键对数量。

若一个桶最终有 `count` 个键，其中的冲突键对数是：

$$
\binom{count}{2}.
$$

```cpp
#include <bits/stdc++.h>
using namespace std;

typedef long long ll;

int bucket_index(ll key, int bucket_count) {
    ll remainder = key % bucket_count;

    if (remainder < 0) {
        remainder += bucket_count;
    }

    return remainder + 1;
}

void solve() {
    int n;
    int bucket_count;
    cin >> n >> bucket_count;

    vector<int> count(bucket_count + 5, 0);

    for (int i = 1; i <= n; i++) {
        ll key;
        cin >> key;
        int index = bucket_index(key, bucket_count);
        count[index]++;
    }

    ll collision_pairs = 0;

    for (int index = 1; index <= bucket_count; index++) {
        collision_pairs += 1LL * count[index] *
                           (count[index] - 1) / 2;
    }

    cout << collision_pairs << '\n';
}

int main() {
    solve();
    return 0;
}
```

输入：

```text
5 7
3 10 16 -4 5
```

`3`、`10` 与 `-4` 都进入同一个同余桶，形成三对冲突；输出：

```text
3
```

## 需要记住什么

1. 哈希函数把什么映射到什么？
2. 相等键与相同哈希值之间，哪个方向必须成立？
3. 为什么有限输出范围必然存在冲突？
4. 分布不均会怎样影响桶的实际长度？
5. 为什么约 $\sqrt H$ 个均匀哈希值就可能出现不可忽略的碰撞风险？
6. 哈希值与桶编号有什么区别？
7. 负数取模结果怎样归一化成合法桶位置？
8. 为什么字符串哈希不放在本篇展开？
