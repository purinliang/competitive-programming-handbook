# 启发式合并

> 最近修订：2026-08-17 08:22 +10:00（未审阅）

有 $n$ 个点，每个点有一种颜色。开始时没有边，随后不断加入无向边。每加入
一条边以后，需要回答：

> 新边所在连通分量中有多少种不同颜色？

并查集可以快速合并连通分量，却只维护父亲和大小等少量信息。若还要知道每个
分量包含哪些颜色，就要为每个连通分量维护一个集合，并在连边时合并两个集合。

直接把第一个集合逐项搬进第二个集合可能很慢：一个很大的集合若反复被搬进
只比它大一点的集合，其中的元素会被重复处理许多次。

启发式合并使用一个极其简单的选择：

> 每次总把较小的容器合并到较大的容器。

这一策略也常称为 small-to-large。它不改变集合并集的结果，只选择代价更低的
合并方向。

## 为什么合并方向不影响答案

设两个连通分量的颜色集合为 $A$ 和 $B$。合并后的颜色集合都是：

$$
A\cup B.
$$

集合并集满足交换律，所以把 $A$ 插入 $B$ 或把 $B$ 插入 $A$，最终内容完全
相同。但是，若插入一个元素需要一定时间，遍历较小集合显然更便宜。

```cpp
if (colors[x].size() < colors[y].size()) {
    swap(x, y);
}

for (int color : colors[y]) {
    colors[x].insert(color);
}
colors[y].clear();
```

交换的是两个根编号 `x` 和 `y`。执行交换以后，`x` 始终表示颜色集合较大的
根，`y` 表示即将被并入并清空的根。

## 为什么一个元素不会被搬运太多次

先考虑所有元素互不重复的情况。一个元素只有在所属容器较小时才会被逐项搬运。
若它从大小为 $s$ 的容器搬入另一个容器，目标容器原本至少也有 $s$ 个元素，
合并后新容器大小至少为 $2s$。

因此，同一个元素每被搬运一次，它所在容器的大小至少翻倍：

$$
1,2,4,8,\ldots,n.
$$

最多翻倍 $O(\log n)$ 次，所以全部 $n$ 个元素的搬运次数为 $O(n\log n)$。

本题中颜色可能重复。插入已经存在的颜色时，这个重复的集合条目会直接消失，
以后不再参与搬运；插入新颜色时则继续享受小并大的增长。重复不会让总工作量
比保留所有独立条目更多。

使用 `set` 时，每次插入还需要 $O(\log n)$ 时间，因此全部集合合并的上界为
$O(n\log^2 n)$。若使用散列表，可在通常情况下把单次插入视为 $O(1)$，但要
承担哈希常数与最坏情况风险。本文选择行为稳定、代码直接的 `set`。

## 与并查集合并方向统一

设 `x` 和 `y` 已经是两个连通分量的根。若它们不同，先保证 `x` 的颜色集合
不小于 `y`：

```cpp
if (colors[x].size() < colors[y].size()) {
    swap(x, y);
}
parent[y] = x;
```

此时让 `y` 的父亲变成 `x`，再把 `colors[y]` 搬入 `colors[x]`。并查集的根与
保存有效颜色集合的下标始终一致。

这里按颜色集合大小选择根，而不是按顶点数量选择根。路径压缩仍然保证后续
查询很快；更重要的是，合并方向必须服务于真正昂贵的颜色集合搬运。

## 重复加入同一分量内的边

加入新边 `(u,v)` 后，先分别找到两个端点的根：

```cpp
int x = find_root(u);
int y = find_root(v);
```

若 `x == y`，这条边没有合并两个连通分量，颜色集合也不应再次合并。直接输出
当前集合大小即可。

## 完整代码

输入先给出每个点的颜色，随后给出 $m$ 条依次加入的无向边。每加入一条边，
输出这条边所在连通分量的不同颜色数量。

```cpp
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<int> parent;
vector<set<int>> colors;

int find_root(int u) {
    if (parent[u] == u) {
        return u;
    }
    return parent[u] = find_root(parent[u]);
}

int merge_components(int u, int v) {
    int x = find_root(u);
    int y = find_root(v);

    if (x == y) {
        return (int)colors[x].size();
    }

    if (colors[x].size() < colors[y].size()) {
        swap(x, y);
    }

    parent[y] = x;
    for (int color : colors[y]) {
        colors[x].insert(color);
    }
    colors[y].clear();

    return (int)colors[x].size();
}

void solve() {
    cin >> n >> m;

    parent.resize(n + 5);
    colors.clear();
    colors.resize(n + 5);

    for (int u = 1; u <= n; u++) {
        int color;
        cin >> color;
        parent[u] = u;
        colors[u].insert(color);
    }

    while (m--) {
        int u, v;
        cin >> u >> v;
        cout << merge_components(u, v) << '\n';
    }
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    solve();
    return 0;
}
```

## 启发式合并解决的是什么

启发式合并不是某一种容器或某一道题的模板。它适用于：

1. 多个容器会不断合并；
2. 合并结果不依赖方向；
3. 遍历并插入一个容器的全部内容是主要代价；
4. 容器被合并以后不再需要保持原内容。

容器中可以保存集合、映射、成员列表或其他可逐项转移的信息。真正需要证明的
始终是：每次搬运以后，元素所在结构的规模是否得到足够增长。

若合并以后仍必须保留两个旧版本，直接清空小容器就不再合法；那是可持久化或
复制语义的问题。若集合还要支持拆分，小并大的单向摊还证明也不能直接套用。

## 与树上启发式合并的关系

树上启发式合并同样利用“保留大的、搬运小的”，但它处理的是树上许多子树
信息的合并，并要配合 DFS 顺序控制哪些统计暂时保留。两者共享摊还思想，
具体遍历过程并不相同。

## 常见错误

- 无论大小，固定把 `x` 合并进 `y`；
- 交换集合以后忘记同步并查集根的方向；
- 两个点已经连通时仍重复搬运颜色集合；
- 合并后继续把旧根的集合当成有效数据使用；
- 只记住“小并大”，却没有确认问题的合并结果是否与方向无关；
- 把 `set` 的单次插入误写成 $O(1)$；
- 合并过程还支持拆分，却继续套用只增不减的翻倍证明。
