# 图示系统设计与长期路线

本文固定 `cp-diagrams` 的架构边界、视觉语法和长期演进顺序。README 负责安装与使用，Schema 文档负责输入格式；本文负责回答“为什么这样分层”和“新增一种图时应放在哪里”。

## 定位

`cp-diagrams` 是面向算法竞赛 handbook 的确定性静态 SVG 图解系统。作者在 YAML 中描述内容、结构和语义强调，程序统一决定坐标、字体、线宽、间距与具体色值。

系统长期覆盖离散结构算法：数组与链式结构、树与区间结构、普通图、排序、图算法和字符串算法。DP、计算几何、动画和 PNG 输出不在当前路线内。

核心约束：

- 输出保持 SVG-only，文字保留为原生 `<text>`。
- 相同输入必须产生逐字节稳定的 SVG。
- YAML 不保存像素坐标、字体、线宽、随机种子或 CSS 色值。
- 优先表达数据结构的本质关系，不追求算法名称数量。
- 新抽象必须由至少一种真实图解需求驱动，不预建空模块或万能接口。

## 分层与依赖

```text
CLI
├── Schema facade
│   ├── version parser / validator
│   └── semantic models
└── Render facade
    └── family renderer
        ├── pure layouts
        ├── shared primitives
        └── Canvas + Theme
                     └── rough SVG backend
```

依赖只能沿箭头向下：

- `models` 只依赖 Python 标准库，不知道 YAML、布局、SVG 或 rough。
- `schema` 只解析和校验作者输入，并构造语义模型。
- `layouts` 只计算坐标、尺寸、层级和端点，不生成 SVG。
- `renderers` 组合模型、布局、共享图元和 Canvas；视觉族之间不互相调用。
- `common/canvas.py` 是唯一可以直接依赖 rough 的模块。
- `render.py` 只负责模型类型分发和文件输出，不承载布局或图元实现。
- `cli.py` 只协调 Schema 与 Render，不绕过公开门面。

目录职责：

| 目录 | 职责 |
| --- | --- |
| `models/` | 与输入、输出技术无关的数组、图、树语义对象 |
| `schema/` | YAML 加载、版本分发、字段校验和结构不变量 |
| `common/` | 主题、字体测量、基础几何类型和 SVG Canvas |
| `layouts/` | 普通图、层级树、区间结构等纯几何算法 |
| `renderers/` | 数组、普通图、普通树、区间树及共享节点/边图元 |
| `tests/golden/` | 正式示例对应的逐字节 SVG 基线 |

## 视觉语法

### 全局规则

- value 是主要信息；index、字段名和辅助标记使用更小的文字层级。
- 字体、字号、基础笔画、强调笔画、虚线节奏和标准间距只由 Theme 提供。
- 普通节点背景只允许白色和深灰色：白底配深灰字，深灰底配白字。旧 Schema 的红、蓝、绿只用于线条、箭头和算法状态强调。
- 节点 `id` 是结构引用。未来普通图 Schema 中必须另给可见 `value`，不把 id/index 当作默认展示内容；v1/v2 的既有行为继续兼容。
- 原数组投影使用分离的虚线格；下标只在原数组保留一套。
- 图宽随内容自然增长，不通过压缩字号或间距适应固定版面。

### 已稳定的视觉族

- 单行与多行数组：共享格宽、文字层级和列对齐规则；前缀和投影可以分离格子，但仍保持数组整体感。
- 普通图：无层级关系时使用确定性平衡布局；自环、边标签和路径强调共享边端口规则。
- 普通树：根据根建立层级；普通有根树按子树宽度分配空间，二叉树保留明确的左右关系。
- 区间树：节点宽度表达覆盖区间。线段树以区间几何中心为结构锚点；树状数组以覆盖区间最后一格的中心为结构锚点。

### 长期视觉族

1. 线性结构：二维/多行数组、栈、队列、单向/双向/环形链表。
2. 层级结构：二叉堆、左偏堆、斜堆、配对堆，以及 AVL、红黑树、Treap、Splay、替罪羊树。
3. 多叉混合结构：B 树与 B+ 树复用“短数组节点＋多叉树布局”，不复制数组和树渲染器。
4. 区间与序列：稀疏表、分块、莫队、归并树、主席树、动态开点线段树、Li Chao 树和 Wavelet Matrix。
5. 森林与特殊树：普通/带权/可撤销并查集、基环树、重链剖分、点分治和虚树。
6. 普通图算法：DFS/BFS、拓扑排序、最短路、最小生成树、连通性分解、欧拉回路、匹配与网络流。
7. 字符串结构：Trie、KMP、Z 函数、Manacher、AC 自动机、后缀数组、后缀自动机和回文树。
8. 过程型算法：用一个 SVG 内的多面板分镜表达排序、链表插删、树旋转、路径压缩、莫队指针和增广路。

可持久化结构使用“多个版本根＋复制路径＋共享未修改子树”；基环树先固定环，再把各环点附着的树向外展开；并查集使用父指针森林，并通过分镜表达路径压缩和按秩合并。

## Schema 与兼容策略

- v1/v2 的合法 YAML、异常语义、CLI 和公开导入路径保持兼容。
- 加入不影响旧输入的新图形类型时，可以继续扩展尚未冻结的版本；修改既有字段含义、默认行为或可见语义时必须建立新版本。
- 多面板分镜是未来独立的 Schema 能力。每个面板包含一个结构状态和可选说明，稳定实体 id 用来维持跨面板位置；在出现第一个真实分镜需求前不提前固定字段形状。
- 旧版本适配停留在 Schema 层，渲染器只接收统一语义模型，不在绘图代码中判断 YAML 版本。

## 扩展准入清单

每加入一种正式图形或布局，必须同时完成：

1. 明确它属于现有视觉族还是确实需要新视觉族。
2. 增加最小语义模型和严格 Schema 校验，不暴露视觉像素参数。
3. 将几何计算放入纯布局函数，将 SVG 操作留在渲染器或共享图元。
4. 增加一个代表本质结构的正式 YAML 示例和对应 golden SVG。
5. 测试合法/非法输入、关键几何不变量、确定性、CLI 与公开接口兼容性。
6. 更新 Schema 文档和本文的视觉族状态。
7. 在全部测试通过并完成视觉审核后形成独立提交。

算法题中的偶然操作不直接成为视觉族。例如“每 k 个删除”或“合并若干链表”应由链表结构、强调和分镜组合表达，而不是各自新增渲染器。

## 拆分原则

- 不按行数机械拆文件；当一个模块开始包含两个能够独立变化的概念时再拆。
- `schema/v2.py` 当前可以整体审查；增加第四种顶层图形类型前，将其拆为数组、图、树解析器及共享节点/边校验。
- `renderers/primitives.py` 当前统一节点、边与 annotation 的端口规则；只有这些规则开始独立演进时，才拆为节点、边和标注图元。
- 数组、图布局和区间树模块达到新视觉子族时，在对应目录内拆分，不建立全局 renderer registry。
- 显式类型分发优先于插件系统；只有第三方扩展成为真实需求时才重新评估注册机制。

## 回归与审查顺序

当前基线要求完整测试、全部正式示例 golden SVG 和 Python 编译检查通过。视觉修改必须更新 golden，并在提交中明确说明它是有意变化。

推荐按以下顺序审查：

1. `models/` 与 `schema/`：输入含义、默认值和错误信息。
2. `common/theme.py` 与 `common/canvas.py`：全局视觉配置和 SVG 输出稳定性。
3. `layouts/`：坐标、锚点、间距与边界裁切。
4. `renderers/`：各视觉族如何组合布局和图元。
5. 正式示例与 golden SVG：最终教学表达是否直观。

依赖边界由测试自动检查；README、Schema 文档和本文共同构成新增功能的审查依据。
